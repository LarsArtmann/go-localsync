Verdict: a deliberately-bounded, well-modularized toolkit

The dependency graph is a clean 5-layer DAG with zero cycles. The architecture uses dependency inversion at the sync/cqrs seam (SyncStore interface defined in pkg/sync, implemented by *cqrs.CQRSStack), a pure contract surface (no provider or CLI in-repo), and a custom AST linter that makes scope drift a build failure. The scope is intentionally bounded by ADR-0004: one aggregate, three events, one projection, pull-only. This is correct sizing for the domain — the SDK is not a framework, and resisting frameworkification is an architectural strength, not a gap.

Layer 0 (leaves) ├── pkg/id ├── pkg/errors ├── pkg/data/schema └── internal/cqrslint (zero internal deps) Layer 1 ├── pkg/data/model → schema, errors, id └── pkg/provider → errors, id Layer 2 ├── pkg/crdt → data/model, id └── pkg/testutil → data/model, provider Layer 3 └── pkg/sync → data/model, data/schema, errors, id, provider Layer 4 └── pkg/cqrs → crdt, data/model, data/schema, errors, id, provider, sync (SyncStore interface) Layer 5 (composition root) └── pkg/api → cqrs, sync, provider, …

The sync/cqrs seam is dependency inversion done right

The orchestrator (pkg/sync) defines SyncStore — a minimal interface with SyncItems, Reconcile, the model.ItemReader methods, and Close. The infrastructure (pkg/cqrs) implements it via thin adapter methods (stack_adapters.go). Because pkg/sync does not import pkg/cqrs, you can swap the CQRS backend for anything else (a flat SQLite table, a Postgres upsert, an in-memory map) without touching the sync engine. This is the Hollywood Principle applied cleanly.

02Scalability Assessment

Dimension Current Verdict
Item volume SQLite via modernc.org (WAL, indexed by type/created_at) Scales to millions per source
Source fan-out Per-source mutex; sources run in parallel CPU-bound, not lock-bound
Horizontal scale Single-process (one writer per aggregate) By design (ADR-0004)
Replay cost Capped by snapshot strategy (EveryNEvents=10) + checkpoint-bounded catch-up Bounded
Provider throughput Concurrent FetchAll pages (default 3); honors rate limits + Retry-After Provider-bound

Scalability ceiling is the single-process boundary — accepted

The SDK is a single-writer pull mirror: one process owns the event store per aggregate. Scaling out to multiple writers would require distributed CRDT machinery (vector clocks, anti-entropy), which was deliberately removed (vector clocks / Operation[T] / SyncMessage deleted; see FEATURES.md #24/#25). For multi-node consumers, ADR-0004 directs sharing go-cqrs-lite directly instead of forcing this SDK into a distributed role it was not designed for. This is the right architectural call — do not “fix” it without revisiting the ADR.

03Composability & Service Orientation

+
Provider is the service boundary The provider.Provider interface (Name/Fetch/FetchAll/GetRateLimit) is the integration contract. Adding a provider = implementing one interface in a consumer app. No SDK changes. Reference impl: github-local-sync.
+
Conflict strategy is pluggable cqrs.CQRSConfig.ConflictResolver accepts any crdt.ConflictResolver[*model.Item]. Default nil = remote-wins. LWWResolver ships in the box; custom merges compose without touching the decider.
+
Backend is selectable CQRSConfig.Backend selects "memory" (testing) or "sqlite" (local) at construction. Event store + read model + snapshots use the same backend. Adding a Postgres backend is a store_factory.go branch, not a rewrite.
+
Read-side and write-side are independently evolvable The decider (write) and read model (read) communicate only via the projection subscription. Reads scale independently; the projection is idempotent so live + catch-up overlap is safe.
+
Architectural invariants are compiled-in internal/cqrslint + cmd/cqrs-lint enforce 10 invariants (single aggregate, 3 events, fold coverage, projection mutex, etc.) at CI time. Future drift toward framework-hood becomes a red CI, not a slow rot.

One coupling note (low priority)

pkg/cqrs imports pkg/sync to see SyncStore + SyncAction. This is documented and intentional (the seam lives in the orchestrator package), but it means the infrastructure package “knows” the orchestrator's vocabulary at compile time. If pkg/cqrs ever needed to be consumed by a different orchestrator, SyncStore/SyncAction would belong in a neutral pkg/contracts package. Not worth doing today — there is exactly one orchestrator and one infrastructure implementation.

04Action Roadmap (Pareto-ordered)

1

Do nothing structural (highest ROI)

The architecture already meets the modularity, composability, and bounded-scope bars. The most valuable architectural action is to keep resisting frameworkification: route any multi-aggregate / push-ingestion / multi-writer request through ADR-0004 review rather than expanding the SDK in place.

2

Optional: external event outflow hook

Consumers that need to react to syncs externally (webhooks, downstream caches) currently have no hook — the bus is internal. An optional CQRSConfig.OnEvent or a documented bus.SubscribeAll entry point would let consumers compose without forking. Non-breaking, additive. Defer unless a consumer asks.

3

Optional: neutral contracts package (if a 2nd orchestrator appears)

Move SyncStore + SyncAction to pkg/contracts so cqrs and sync both depend downward on it, removing the upward edge. Only justified by actual demand — today it would add a package for one consumer.

Bottom line Layered, inverted, bounded, and invariant-enforced. The architecture is the kind you preserve, not the kind you redesign. The only “scalability ceiling” is single-process — and that is a deliberate, ADR-recorded decision, not a defect.
