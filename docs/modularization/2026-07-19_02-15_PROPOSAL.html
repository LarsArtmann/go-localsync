Recommendation: keep the single module. Do not split.

The go-modularize skill is direction-neutral — both “too many modules” and “too few modules” are failures of the same kind. Applied to go-localsync, the evidence points clearly to keep the current single go.mod. The project is one focused domain (single-aggregate pull-mirror sync), its 12 packages compose only at the application level (no consumer imports a subset), and the existing package-level boundaries are already enforced by import-direction + a custom AST linter. Splitting would add multi-module overhead (go.work/replace drift, vendor friction) with zero composability payoff. This is the skill's endorsed “partial / no-op outcome” — not every project needs 5+ modules.

Composability payoff test (the deciding factor)

Question: Does any consumer import module A without module B? If yes, the boundary earns its keep. If every consumer imports A and B together, the seam earns nothing.

Answer for go-localsync: Every consumer wires sync.NewSyncer(provider, cqrsStack, ...). The packages are designed to compose at the application boundary, not to be picked à la carte. There is no consumer that wants pkg/cqrs without pkg/sync, or pkg/crdt without pkg/data/model. Independent versioning would impose release-coordination cost with zero selectivity benefit.

Co-change analysis (last 20 commits)

commits touching ├── single package (cqrs alone, sync alone, errors alone): majority ├── cqrs + sync together: 1 commit ├── cqrs + errors together: 1 commit └── all-packages sweep: 1 commit (scope-pivot refactors)

Co-change is driven by feature work, not artificial coupling. This is evidence the package boundaries are correctly placed — and package boundaries (not module boundaries) are the right granularity here.

02Alternatives Considered (and rejected)

Rejected

Extract pkg/id + pkg/data/model into a versioned localsync-domain module

proposed new module: github.com/larsartmann/go-localsync-domain

Pitch: decouple the domain types from the infrastructure so multiple infrastructure implementations could version independently.

Why rejected: there is exactly one infrastructure implementation (pkg/cqrs) and it lives in the same repo. A domain module is only worth extracting when a second infrastructure appears (or when external consumers need the types without the engine). Today this would create a module with 2 packages, no independent consumers, and a new version-sync burden. Revisit only if ADR-0004's multi-aggregate deferral is ever reversed.

Rejected

Extract pkg/testutil into a separate localsync-testutil module

proposed new module: github.com/larsartmann/go-localsync-testutil

Pitch: keep test-only helpers out of the production module so consumers don't pull test deps.

Why rejected: this is Failure Mode #3 (test-dep leaks) misdiagnosed as a boundary problem. pkg/testutil is already only imported by _test.go files (verified: zero production imports). Go's tooling already excludes test-only import costs from consumer builds. Extracting a module to solve a non-leak is the “hygiene trap” the skill explicitly warns against.

03Hygiene Notes (not boundary problems)

Two real go.mod hygiene issues exist, but neither is a modularization problem and neither is cured by splitting/merging:

  • Committed vendor/ for a private dep. go-cqrs-lite is private, forcing vendorHash = null in flake.nix and a force-added vendor/ tree. The clean fix (already tracked in TODO_LIST.md) is to make go-cqrs-lite public, then drop vendor/ and use a real vendorHash. Merging or splitting localsync modules does nothing here.
  • go.work is a local-dev-only file (gitignored). It must never be committed or left on disk during buildflow. This is documented in AGENTS.md. Again, orthogonal to module boundaries.
Bottom line The current single-module layout is the correct boundary for a focused, pre-1.0, single-domain SDK. Package-level seams (import direction, the SyncStore interface, cqrs-lint invariants) already deliver the compile-time isolation that multi-module would promise — without the go.work/vendor overhead that AGENTS.md already flags as painful. No action.
