1. Executive Overview

The pkg/data/ module is a newly-built data layer that attempts to separate concerns between providers, domain, views, and APIs using Go generics. It introduces layered data types (ProviderItem → Item → ItemView), a generic query DSL, composable transformers, and schema versioning. The intent is excellent. The execution is solid but not superb. A detailed comparison against go-cqrs-lite v2.1.0 (the upstream CQRS framework this project already depends on) reveals that several "innovations" in this module are actually inferior reinventions of patterns go-cqrs-lite solved more robustly — with real dialect abstraction, working schema upcasters, and production-grade observability hooks.

Core Insight

This module correctly identifies the fundamental problem: provider.Item was doing four jobs (DTO, domain entity, read model, API response). The solution introduces explicit types per layer with transformations between them. But several design decisions reveal inexperience with Go's type system — missed opportunities for structural typing, over-reliance on getter methods for generics, and SQL generation that undermines type safety.

4. Deep Dive: What's Right & Wrong

4.1 Model Layer — The Good

Correct Composite Key Type

The Key struct with Source and ExternalID branded IDs is exactly right. It makes the composite identity explicit and type-safe. You cannot accidentally pass an ExternalID where a Source is expected. 

type Key struct {
    Source     id.ProviderID
    ExternalID id.ExternalID
}
Correct Layered Types

Separating ProviderItem (has RawPayload) from Item (clean domain) from ItemView (has computed fields) is architecturally sound. The dependency graph is one-way: Provider → Domain → View → API.

4.2 Model Layer — The Problems

Getter Method Proliferation

Every field on Item has a corresponding Get*() method. These exist solely to satisfy the interface constraints in query.HasSource[T] etc. This is 14 methods of pure boilerplate that accomplish nothing. 

// 7 accessor methods on Item...
func (item Item) GetSource() id.ProviderID { return item.Source }
func (item Item) GetType() id.EventTypeID   { return item.Type }
// ...and 7 more on ItemView. Total: 14 lines of noise.

Why this hurts: Go's structural typing means these methods are discoverable only by reading the source. They're not part of any named interface. A better approach uses field tags + reflection, or — preferably — makes criteria closure-based without interface constraints.

Schema Versioning Is a Stub

The schema.Version type has constants and a Valid() method, but no actual migration logic. The event store's ItemSyncedPayload doesn't carry a schema version, so old events cannot actually be migrated. 

// What exists: version constants
const (
    V1 Version = 1
    V2 Version = 2
)

// What's missing: migration functions, payload versioning, rollback support

4.3 Query Layer — The Good

Excellent Generic Criterion Interface

Criterion[T] with both Match(T) bool and ToSQL() is a powerful abstraction. It lets the same query run in-memory (for tests) and in SQL (for production) without code duplication. 

type Criterion[T any] interface {
    Match(value T) bool
    ToSQL() (clause string, args []any)
}
Good Logical Combinators

And[T], Or[T], and Not[T] are generic logical combinators. They compose criteria cleanly and produce valid SQL. This is a genuinely useful generic pattern.

4.4 Query Layer — The Problems

SQL String Concatenation Is Dangerous

The And and Or combinators build SQL by string concatenation. While the individual criteria use ? placeholders, the combinator wraps clauses in parentheses using fmt.Sprintf("(%s)", clause). This is safe for the current implementation but fundamentally fragile. 

func And[T any](criteria ...Criterion[T]) Criterion[T] {
    // ...match logic is fine...
    return NewCriterion(nil, func() (string, []any) {
        // This builds SQL strings. It's not type-safe and doesn't support
        // dialect differences (SQLite vs PostgreSQL vs MySQL).
        return strings.Join(clauses, " AND "), args
    })
}

Better approach: Separate query compilation from execution. Introduce a QueryCompiler interface with dialect-specific implementations. Or better yet: use a proper query builder like squirrel or sqlc.

No Query Plan or Optimization

The Query[T] type carries no metadata about which fields are indexed. A query on actor_login (which has an index) and repo_url (which does not) are treated identically. There's no way to:

  • Warn about unindexed queries
  • Reorder criteria to put the most selective first
  • Generate EXPLAIN-style debugging output

Query.Sort Mutates In-Place

The Query.Sort() method calls slices.SortFunc(items, ...) which mutates the input slice. But the Query is documented as "immutable." This is inconsistent. Either make Sort return a new slice, or don't claim immutability.

4.5 Transform Layer — The Good

Excellent Generic Mapper with Composition

The Mapper[From, To] interface with Compose[A,B,C] is the single best piece of code in this module. It enables type-safe, testable, composable transformations. 

// Compose two mappers into a pipeline
var ProviderToView = Compose(
    FromProviderItem,   // *ProviderItem → *Item
    ToItemView,         // *Item → *ItemView
) // *ProviderItem → *ItemView

4.6 Transform Layer — The Problems

Context Is Unused in Most Mappers

Every mapper takes context.Context but none of the current implementations use it. This is premature abstraction — add context when you need it (e.g., for tracing or cancellation), not before. The unused parameter is a code smell.

No Batch Mapping

The Mapper interface only maps one item at a time. For a sync operation that processes 10,000 items, this means 10,000 individual allocations. A batch mapper: 

// What's missing: batch transformation
type BatchMapper[From, To any] interface {
    MapBatch(ctx context.Context, from []From) ([]To, error)
}

Error Context Is Lost in Composition

The Compose function wraps errors with generic messages like "compose A→B". When a pipeline of 5 mappers fails, you get a nested error that doesn't tell you which field was invalid or which item caused the problem.

4.7 Repo Layer — The Problems

Observable Is a No-Op Decorator

The Observable[T] struct claims to "add metrics/logging" but implements nothing. It just delegates every call to the base reader. This is dead code dressed up as a decorator pattern. Either implement it properly or delete it. 

func (o *Observable[T]) Get(ctx context.Context, key model.Key) (T, error) {
    // TODO: actually log/measure something
    return o.base.Get(ctx, key)
}

No Transaction Support

The repository interfaces have no concept of transactions. You cannot atomically upsert multiple items or ensure that a sync operation is all-or-nothing. For CQRS with event sourcing, this is a critical gap.

ItemRepository Interface Is Awkward

ItemRepository embeds Repository[*model.ItemView] but adds two methods (GetTypes, GetStats). The stats method returns model.StatsView by value — if stats are large, this copies maps. And there's no way to get stats with a filter.

5. Path to Perfection

To get from "solid" to "superb," we need to address five areas: eliminate getter boilerplate, make SQL generation safe, add real observability, support transactions, and implement actual schema migration. Here's how.

5.1 Kill the Getter Methods — Use Struct Tags

Current (14 methods)
func (item Item) GetSource() id.ProviderID
func (item Item) GetType() id.EventTypeID
func (item Item) GetActorLogin() id.ActorID
// ... 11 more
→
Better (0 methods)
type Item struct {
    Source     id.ProviderID  `data:"source,indexed"`
    Type       id.EventTypeID `data:"type,indexed"`
    ActorLogin id.ActorID     `data:"actor_login"`
    CreatedAt  time.Time      `data:"created_at,indexed,sort"`
}

Why This Is Better

Struct tags let us generate criteria, SQL, and indexes from reflection — once. The data tag carries: column name, whether it's indexed, whether it supports sorting, and the SQL type. A single go generate pass produces the criteria constructors that currently require 7 generic functions with interface constraints. The generated code is as fast as hand-written, but the source of truth is the struct definition.

5.2 Replace SQL Strings with a Type-Safe AST

String-based (fragile)
func (c CriterionFunc[T]) ToSQL() (string, []any) {
    return c.sqlFn()
}

// Combinator concatenates strings:
return strings.Join(clauses, " AND "), args
→
AST-based (safe)
type Expr interface {
    SQL(dialect Dialect) (string, []any)
}

type Eq struct { Column string; Value any }
type And struct { Exprs []Expr }
type Or  struct { Exprs []Expr }

Why This Is Better

An AST makes SQL generation structural, not textual. You can:

  • Validate the tree before generating SQL (no injection)
  • Optimize: reorder AND clauses to put indexed fields first
  • Support dialects: SQLite uses ?, PostgreSQL uses $1
  • Generate EXPLAIN output for debugging slow queries
  • Test the AST without a database

5.3 Add Real Observability with Middleware

The Pattern: Decorator Chain

type MetricsDecorator[T any] struct {
    base    repo.Reader[T]
    metrics MetricsRecorder
}

func (d *MetricsDecorator[T]) List(ctx context.Context, q query.Query[T]) (query.Page[T], error) {
    start := time.Now()
    page, err := d.base.List(ctx, q)
    d.metrics.Record("repo.list", time.Since(start), err)
    return page, err
}

Replace the no-op Observable with a proper decorator chain: LoggingDecorator → MetricsDecorator → CacheDecorator → BaseRepo. Each decorator implements Reader[T] and adds one concern. Compose them with a builder, not by hand.

5.4 Add Transaction Support

Unit of Work Pattern

type UnitOfWork interface {
    Begin() error
    Commit() error
    Rollback() error
    Items() repo.Writer[*model.Item]
    Events() event.Store
}

A Unit of Work coordinates writes across the read model and event store. In CQRS, a sync operation should: (1) write events to the event store, (2) project them to the read model, (3) commit both atomically. Without transactions, a crash after step 1 but before step 2 leaves the system inconsistent.

5.5 Implement Real Schema Migration

Versioned Migrations with Type Safety

type Migration struct {
    From    schema.Version
    To      schema.Version
    Migrate func(map[string]any) (map[string]any, error)
}

var Migrations = []Migration{
    {From: schema.V1, To: schema.V2, Migrate: addSchemaVersionField},
    {From: schema.V2, To: schema.V3, Migrate: addConflictHistory},
}

// Event payload carries version:
type ItemSyncedPayload struct {
    // ...fields...
    SchemaVersion int `json:"schemaVersion"`
}

Every event payload must carry its schema version. On replay, the projection migrates the payload forward before applying it. This makes old events forward-compatible without rewriting the event store.

5.6 Add Batch Operations

Batch Mapper for Sync Performance

type BatchMapper[From, To any] interface {
    MapBatch(ctx context.Context, from []From) ([]To, error)
}

// Concrete implementation with pre-allocated capacity:
func (m *providerMapper) MapBatch(ctx context.Context, items []*model.ProviderItem) ([]*model.Item, error) {
    result := make([]*model.Item, 0, len(items))
    for _, p := range items {
        item, err := m.Map(ctx, p)
        if err != nil {
            return nil, fmt.Errorf("item %s: %w", p.ExternalID, err)
        }
        result = append(result, item)
    }
    return result, nil
}

Batch operations pre-allocate capacity and collect errors with context (which item failed). For a 10,000-item sync, this avoids 10,000 small allocations and gives actionable error messages.

5.7 Add Connection Pool and Dialect Abstraction

Database Handle with Dialect

type Handle interface {
    QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
    ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
    Dialect() Dialect
}

type Dialect interface {
    Placeholder(n int) string  // "?" or "$1"
    Quote(name string) string      // "name" or `name`
    Limit(limit, offset int) string
}

Abstracting the database handle lets the same repository implementation work with SQLite (local), PostgreSQL (production), and even in-memory stores. The dialect handles placeholder syntax, identifier quoting, and LIMIT/OFFSET syntax differences.

Bottom Line

The current data module is a good first draft. It correctly identifies the architectural problem (one struct for all layers) and applies the right solution (explicit types with transformations). But it falls short on execution: SQL generation is string-based, observability is a stub, and the generic constraints force boilerplate getter methods.

The path to superb requires three big moves: (1) struct tags + code generation to eliminate getters, (2) an SQL AST to make query compilation safe and optimizable, and (3) a UnitOfWork pattern with real decorators for transactions and observability. These are not cosmetic changes — they fundamentally change how the module compiles queries, tracks performance, and guarantees consistency.
