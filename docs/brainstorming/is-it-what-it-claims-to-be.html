Is It What It Claims To Be?

A diagnostic session on go-localsync: brutal audit, two course corrections, and the single fork that decides the entire architecture.

Date: 2026-06-27

Bottom line

The CQRS persistence core is genuinely good. The sync engine draped over it is uncommitted — a pull mirror wearing a few of two-way-sync's clothes (DeleteItem, vector clocks, SyncRequest) with none of them wired. Worse, the public Sync() API silently drops data while returning nil error — the worst failure mode a sync product can have.

The path to "superb" is not adding features. It's fixing the silent-data-loss paths, killing the phantom surfaces, and committing to one identity — pure pull mirror, or offline two-way sync. Everything hangs on that one choice.

1The CRDT Theater Characterization

The session opened with a sharp claim about go-localsync's current state, which was verified against the actual code and confirmed accurate. Four claims, all true:

  • ConflictResolver / LWWResolver are wired in to the decider.
  • VectorClock, Operation[T], SyncMessage, SyncRequest are implemented and tested but not wired — zero references outside pkg/crdt/ self-tests.
  • The flow is strictly provider → local PULL, single-directional. No push path exists.
  • Vector clocks are always empty (crdt.NewVectorClock()) when LWW runs, so the causal branch is structurally unreachable — LWW always falls through to timestamp comparison.

Wired vs. theater

Thing Reality Status
ConflictResolver[T] interface Wired through CQRSConfig → decideSync (decider.go:77,165) Wired
LWWResolver[T] The only concrete impl — referenced only in tests/docs. Default path is resolver == nil → remote-wins short-circuit. Tests only
VectorClock Constructed at decider.go:175 but always empty. Never populated. Decorative
Operation[T], SyncMessage, SyncRequest, SyncResponse Zero references in pkg/cqrs/ or cmd/. Used only in pkg/crdt/ self-tests. Dead code

Net characterization

It's YAGNI infrastructure with a documentation alibi. The CRDT package isn't wrong — it's a correct, tested foundation for a multi-node future that ADR-0003 deliberately defers. The mild smell is calling this "CRDT conflict resolution" in marketing when production behavior is plain last-write-wins on UpdatedAt with a plugin seam nobody plugs anything into.

2The Thesis: Superb ≠ Featureful

The user's challenge, verbatim:

" Let's actually fucking create a superb SDK that handles all edge cases so superbly 99% of developers would fall out of their chair… INSTEAD OF CREATING ANOTHER DOGSHIT PROGRAM! — Lars, opening the session

The trap to avoid

The instinct is to add — wire up the CRDT theater, build multi-node, add push. That's how you build a second dogshit program: by adding features to mask a weak foundation.

What "superb" actually means here

For a pull-sync SDK, superb means three things — and only three:

  1. It never silently loses or corrupts data — every partial failure, race, and edge case has a defined, correct outcome.
  2. It's honest about what it is — no speculative types pretending to be an architecture.
  3. It's invisible to users because it just works — consumer devs wire a provider in 20 lines and never think about it again.

Less surface, zero lies, every edge case defined. Trustworthy, not featureful.

3Data Integrity — What Corrupts User Data

The decider, the event sourcing, the read-model projection — every place data could be silently lost or corrupted.

Critical — silent data loss / corruption
High — data loss under realistic conditions
Medium — correctness risk under edge cases
# Failure Severity Where
1 No upstream-deletion detection. Items the provider stops returning live forever. No tombstone, no reconciliation. Add/update-only. Critical sync/sync.go:72
2 Aggregate-ID colon collision → two distinct items corrupt one event stream. The ":" separator isn't length-prefixed or escaped. Critical aggregate_id.go:13
3 hasChanged ignores ActorAvatarURL & RawJSON → real updates silently dropped. Avatar URLs drift constantly in the wild. High decider.go:234
4 Resurrect bypasses conflict resolution → stale data reinstated unconditionally when a deleted item reappears. High decider.go:83
5 Live + background replay overlap resurrects deleted rows in the read model during startup catch-up. The "no checkpoint needed" comment is wrong under reordering. High runner.go:17
6 LWW with provider clocks, no skew guard; vector clocks always empty. A fast provider clock always wins. High decider.go:172
7 OCC not enforced by localsync; concurrent same-item syncs can diverge. Relies entirely on go-cqrs-lite's version check. Medium decider.go:80
8 Schema upcasting not implemented; entire "upcasting" is if v==0 { v=V1 }. Future schema changes = silent zero-fills. Medium version.go

Detail: the aggregate-ID collision

// pkg/cqrs/aggregate_id.go:13
func itemKey(source string, externalID id.ExternalID) string {
    return source + ":" + externalID.Get()
}

Two distinct items collide: source="github", externalID=":42" → key "github::42" and source="github:", externalID="42" → key "github::42". Both hash to the same AggregateID → their events interleave in one aggregate → cross-item corruption. Fix length-prefixed encoding or null-byte separator before hashing.

Detail: hasChanged false-negative

// pkg/cqrs/decider.go:234
func hasChanged(local, remote *model.Item) bool {
    return !local.UpdatedAt.Equal(remote.UpdatedAt) ||
        local.Type.Get() != remote.Type.Get() ||
        local.ActorLogin.Get() != remote.ActorLogin.Get() ||
        local.RepoName.Get() != remote.RepoName.Get() ||
        local.RepoURL != remote.RepoURL
}

Not compared: ActorAvatarURL, CreatedAt, ExternalID, Source, SchemaVersion, and crucially RawJSON (the actual provider payload). If hasChanged returns false → return nil, nil → the update is silently dropped. Should compare a content hash of RawJSON.

4Sync Loop & Resilience Audit

The sync engine draped over the CQRS core is a facade. The resilience knobs are all declared, none enforced.

The worst property: Sync() always lies

sync.go:99 — Sync() returns (*SyncResult, error) but the error is structurally always nil, even when hundreds of items fail. Per-item errors are swallowed into an integer counter; the caller cannot tell which items failed or why.

This is the single worst failure mode a sync product can have: silently dropping data while returning green.

# Area Severity Verdict
1 Partial failure High Partial commit; Sync always returns nil even when hundreds fail; per-item detail discarded.
2 Rate limiting Critical RateLimitConfig/RateLimitCache are dead code. No Retry-After, no backoff. Will hammer a 429'd API.
3 Retry Critical RetryConfig is dead code. Only retry wired in is on CQRS command dispatch, not provider fetch. IsRetryable unused.
4 Pagination Critical No FetchAll impl ships. FetchConfig/MaxConcurrentFetches unused. Memory unbounded by contract.
5 Observability High Progress callback fires once at end. No metrics. Skips are log-only. Top-level result hides per-item failures.
6 Graceful shutdown High ctx propagated but never checked in the batch loop. Cancel mid-batch runs to completion.
7 Ergonomics Medium No example, no cmd/, no provider. ~10 concepts to first sync; consumer writes all the hard parts.
8 Error taxonomy High Clean Rejection/Transient/Infrastructure model exists and is consulted nowhere.
9 Concurrency Medium No global lock; safe at CQRS layer; racy at Syncer/incremental layer (TOCTOU on latest timestamp).

Net

The SDK is a CQRS/CRDT persistence core wearing a "sync engine" overcoat. The overcoat has no buttons: the provider contract is unimplemented, the resilience knobs (RetryConfig, RateLimitConfig, FetchConfig, IsRetryable) are inert, and the public Sync API actively conceals failure. Under real load against a real flaky provider, an operator will see items silently dropped, no retries, no rate-limit respect — and a green "no error" return.

5The Boundary: Move to go-cqrs-lite?

User asked: "Maybe we actually just need to move some of the capabilities currently in this project to go-cqrs-lite or a new submodule of it?"

go-cqrs-lite is a 43-module CQRS + Event Sourcing library (v3.1.0) that deliberately excludes all distributed-systems sync primitives. Its charter (docs/ECOSYSTEM_BOUNDARIES.md) explicitly assigns CRDT/conflict logic to go-localsync, out of cqrs-lite.

The key insight: pkg/crdt/ is two unrelated things wearing one name

Cluster A

Generic conflict resolution

Conflict[T], ConflictResolver[T], LWWResolver[T]

A plain strategy pattern: "two candidate values arrive for one aggregate, which wins?" Generic over T. Not a CRDT — LWWResolver is literally "compare two timestamps." Every event-sourced app needs this policy.

Genuinely used

Cluster B

Distributed delta-CRDT sync

VectorClock, Operation[T], SyncMessage, SyncRequest, SyncResponse[T]

Multi-node delta-exchange protocol types. Real CRDTs. Useful only when ≥2 nodes exchange deltas. Zero non-test references anywhere.

Dead

Why this matters

The crdt/ name lied to the boundary doc, and that lie is why everything feels tangled. ConflictResolver[T] isn't a CRDT — so migrating it doesn't violate the charter. The actual CRDTs are Cluster B.

The recommended three-way split

1. Cluster A → new go-cqrs-lite/conflict/v3

The only migration that creates real value. Every event-sourced app needs a "what wins on conflicting writes" policy; today go-cqrs-lite's sole answer is "reject with a Conflict error and retry." A resolve/merge strategy fills a genuine gap. Isn't a CRDT — doesn't violate the charter. Amend the doc: generic conflict resolution IN, distributed CRDT merge OUT.

2. Cluster B → delete (or defer) challenged in §6

Moving dead code to a new home doesn't make it alive — it just relocates the facade. If/when a second node exists, revive into a correctly-named go-crdt-lite.

3. The model.Item-coupled half of pkg/cqrs/ stays

It's the domain. The generic wiring helpers (stack.go, store_factory.go) could eventually graduate to go-cqrs-lite/stack once de-domain-ified — not worth the cost now.

Crucial caveat

Don't let "move things to cqrs-lite" become a way to avoid fixing the bleeding. Migration is orthogonal to the data-integrity bugs. The collision, the hasChanged data loss, the lying Sync() — those stay broken regardless of where the types live.

6Vector Clocks: Defense → Retraction

User pushed back: "VectorClock's sound cool though, and can solve real problems specially in cases where some emitter may not have internet for a while."

First: a defense (partially correct)

Vector clocks earn their keep the moment an aggregate has ≥2 potential writers. The claim was that stack.DeleteItem was already a second writer (local delete vs remote update), making vector clocks the principled fix for a real present-day bug.

Scenario Does LWW lose data? Do vector clocks fix it?
Provider re-sorts/updates a live item No (one writer) No-op (correct)
Local delete + remote update interleave Yes Yes
Offline emitter buffers edits, reconnects Yes Yes
Multi-source merge of cross-posted items Yes Yes — only if items unify into one aggregate

The honest problem isn't the types — it's the empty wiring

The types are correct. VectorClock, Operation[T] are textbook-correct, well-tested. Not theater. The lie is the empty construction in the decider — crdt.NewVectorClock() on every conflict, making the causal branch structurally unreachable while pretending it was consulted.

So "delete the cluster" was the wrong prescription. The right one: keep the types, kill the empty-wiring, decide whether to wire them for real.

Then: the retraction

This entire defense rested on stack.DeleteItem being a live second writer. The next question exposed that assumption as false. See §7.

7The DeleteItem Discovery

User's two-word reaction to the stack.DeleteItem claim: "We have Delete?"

Verified: DeleteItem exists at stack.go:154. But who calls it?

Surface Calls DeleteItem?
pkg/api/ (HTTP server) No
pkg/sync/ (sync loop) No
cmd/ No
Tests Yes — 8 test files

Full retraction of the vector-clock defense

If DeleteItem is never called outside tests, there is no second writer. The provider is the sole writer to every aggregate. Which means:

  • The resurrect bug (local delete vs remote update) cannot occur in the running system — nothing writes the delete.
  • Vector clocks genuinely have no live justification today.
  • Pure LWW-by-timestamp is, for the actual single-writer model, a defensible strategy — the problem was the empty vector-clock construction pretending it was consulted.

DeleteItem, RateLimitConfig, RetryConfig, crdt.SyncMessage: all the same disease — implemented, unit-tested surfaces with no caller in the live system.

" It's not under-built, it's uncommitted. — the real diagnosis, after the retraction

8The Open Fork: What Is go-localsync?

This is the single product-identity decision that shapes everything downstream. Nothing else can be decided until it is.

One decision. Everything hangs on it.

Is this a pure pull mirror or an offline-capable two-way sync engine?

Option A Pure pull mirror

Read-only local projection of upstream. SDK only ever adds/updates from provider. Deletion = "provider stopped returning it" → reconciliation diff.

What happens to each surface:

  • ✕ DeleteItem → delete the orphan
  • ○ Vector clocks → dormant, honestly stubbed
  • → Upstream deletion → set-diff reconciliation
  • ✕ Cluster B CRDT types → delete

Honest, tiny surface, vector clocks correctly absent.

OR

Option B Offline two-way sync

Local mutations (delete/edit) buffer and reconcile with upstream later. "Emitter loses internet" is a real scenario. DeleteItem is the seed of the real product.

What happens to each surface:

  • ✓ DeleteItem → wire to API + sync loop
  • ✓ Vector clocks / HLC → actually populate
  • ✓ Causal history tracked, offline edits reconcile
  • ▲ Much bigger scope — eat the schema migration

A real product — but a real commitment.

Why this can't be deferred

Every other question in this document is downstream of A vs B:

Concern Under A Under B
Fix order Both fix the bleeding first. Only A then stops. Also must wire DeleteItem + causality.
Migration scope Both move Cluster A to conflict/v3. Only A deletes Cluster B. Keeps Cluster B; wires it for real.
Resurrect handling Moot — no delete path exists. Real bug; vector clocks / HLC fix it.
Marketing honesty "Pull mirror" is honest. "Two-way offline sync" must become true.

Recommended sequence (regardless of A or B)

  1. Fix the bleeding first — aggregate-ID collision, hasChanged content-hash, lying Sync() → real per-item errors. Pure localsync, no migration dependency.
  2. Decide A vs B. This is the pivot.
  3. Then: migrate ConflictResolver[T] → go-cqrs-lite/conflict/v3; and either delete the dead CRDT cluster (A) or wire causality for real (B).
