1. Opening: The CRDT Theater Characterization

The session opened with a sharp claim about go-localsync's current state, which was verified against the actual code and confirmed accurate:

  • ConflictResolver / LWWResolver are wired in to the decider.
  • VectorClock, Operation[T], SyncMessage, SyncRequest are implemented and tested but not wired — zero references outside pkg/crdt/ self-tests.
  • The flow is strictly provider → local PULL, single-directional. No push path exists.
  • Vector clocks are always empty (crdt.NewVectorClock()) when LWW runs, so the causal-ordering branch is structurally unreachable — LWW always falls through to timestamp comparison.
  • ADR-0003 explicitly defers all of this as "future multi-node work."

What's genuinely wired vs. what's theater

Thing Reality Status
ConflictResolver[T] interface Wired through CQRSConfig → decideSync (pkg/cqrs/decider.go:77,165) Wired
LWWResolver[T] The only concrete impl — referenced only in tests/docs. Default production path is resolver == nil → remote-wins short-circuit. Tests only
VectorClock Constructed at decider.go:175-176 but always empty. Never populated. Decorative
Operation[T], SyncMessage, SyncRequest, SyncResponse Zero references in pkg/cqrs/ or cmd/. Used only in pkg/crdt/ self-tests. Dead code

The net characterization

It's YAGNI infrastructure with a documentation alibi. The CRDT package isn't wrong — it's a correct, tested foundation for a multi-node future that ADR-0003 deliberately defers. The mild smell is calling this "CRDT conflict resolution" in marketing when production behavior is plain last-write-wins on UpdatedAt with a plugin seam nobody plugs anything into. The system today is: single-node, pull-only, remote-wins LWW by timestamp, with a well-built but dormant CRDT layer.

2. The Thesis: Superb ≠ Featureful

The user's challenge: "Let's actually fucking create a superb SDK that handles all edge cases so superbly 99% of developers would fall out of their chair… INSTEAD OF CREATING ANOTHER DOGSHIT PROGRAM!"

The trap to avoid

The instinct is to add — wire up the CRDT theater, build multi-node, add push. That's how you build a second dogshit program: by adding features to mask a weak foundation.

What "superb" actually means here

For a pull-sync SDK, superb means three things — and only three:

  1. It never silently loses or corrupts data — every partial failure, race, and edge case has a defined, correct outcome.
  2. It's honest about what it is — no speculative types pretending to be an architecture.
  3. It's invisible to users because it just works — consumer devs wire a provider in 20 lines and never think about it again.

Less surface, zero lies, every edge case defined. Trustworthy, not featureful.

Before proposing a single line of code, the actual failure surface had to be mapped. Two deep audits followed.

3. Data Integrity Audit — What Corrupts User Data

The decider, the event sourcing, the read-model projection — every place data could be silently lost or corrupted.

The bleeding: confirmed data-loss & corruption vectors

# Failure Severity Where
1 No upstream-deletion detection. Items the provider stops returning live forever. No tombstone, no reconciliation diff. Add/update-only against the provider. Critical sync/sync.go:72-116
2 Aggregate-ID colon-delimiter collision → two distinct items corrupt one event stream. The ":" separator isn't length-prefixed or escaped. Critical cqrs/aggregate_id.go:13
3 hasChanged ignores ActorAvatarURL & RawJSON → real updates silently dropped. Avatar URLs drift frequently in the wild. High cqrs/decider.go:234
4 Resurrect bypasses conflict resolution → stale data reinstated unconditionally when a deleted item reappears. High cqrs/decider.go:83-85
5 Live + background replay overlap resurrects deleted rows in the read model during startup catch-up. The "idempotent, no checkpoint needed" comment is wrong under reordering. High cqrs/runner.go:17
6 LWW with provider clocks, no skew guard; vector clocks always empty (dead code). A provider with a fast clock always wins. High cqrs/decider.go:172-178
7 OCC not enforced by localsync; concurrent same-item syncs can diverge. Relies entirely on go-cqrs-lite's expected-version check. Medium cqrs/decider.go:80,105
8 Schema upcasting not implemented; the entire "upcasting" is if v==0 { v=V1 }. Future schema changes = silent zero-fills. Medium data/schema/version.go

Detail: the aggregate-ID collision

// pkg/cqrs/aggregate_id.go:13-15
func itemKey(source string, externalID id.ExternalID) string {
    return source + ":" + externalID.Get()
}

Two distinct items collide: source="github", externalID=":42" → key "github::42" and source="github:", externalID="42" → key "github::42". Both hash to the same AggregateID → their events interleave in one aggregate → cross-item corruption. Fix: length-prefixed encoding or null-byte separator before hashing.

Detail: hasChanged false-negative

// pkg/cqrs/decider.go:234-240
func hasChanged(local, remote *model.Item) bool {
    return !local.UpdatedAt.Equal(remote.UpdatedAt) ||
        local.Type.Get() != remote.Type.Get() ||
        local.ActorLogin.Get() != remote.ActorLogin.Get() ||
        local.RepoName.Get() != remote.RepoName.Get() ||
        local.RepoURL != remote.RepoURL
}

Not compared: ActorAvatarURL, CreatedAt, ExternalID, Source, SchemaVersion, and crucially RawJSON (the actual provider payload). If hasChanged returns false → return nil, nil → the update is silently dropped. Should compare a content hash of RawJSON.

4. Sync Loop & Resilience Audit — The Inert Knobs

The sync engine draped over the CQRS core is a facade. The resilience knobs are all declared, none enforced.

The worst property: Sync() always lies

sync.go:99-115

Sync() returns (*SyncResult, error) but the error is structurally always nil, even when hundreds of items fail. Per-item errors are swallowed into an integer counter; the caller cannot tell which items failed or why. This is the single worst failure mode a sync product can have: silently dropping data while returning green.

# Area Severity One-line verdict
1 Partial failure High Partial commit; Sync always returns nil error even when hundreds of items fail; per-item detail discarded.
2 Rate limiting Critical RateLimitConfig/RateLimitCache are dead code. No Retry-After, no backoff, no enforcement. Will hammer a 429'd API.
3 Retry Critical RetryConfig is dead code. Only retry wired in is on CQRS command dispatch, not provider fetch. IsRetryable unused.
4 Pagination Critical No FetchAll implementation ships. FetchConfig/MaxConcurrentFetches unused. Memory unbounded by contract.
5 Observability High Progress callback fires once at end. No metrics. Skips are log-only. Top-level result hides per-item failures.
6 Graceful shutdown High ctx propagated but never checked in the batch loop. Cancel mid-batch runs to completion. No partial-state reporting.
7 Ergonomics Medium No example, no cmd/, no provider. ~10 concepts to first sync; consumer writes all the hard parts.
8 Error taxonomy High Clean Rejection/Transient/Infrastructure model exists and is consulted nowhere.
9 Concurrency Medium No global lock; safe at CQRS layer; racy at Syncer/incremental layer (TOCTOU on latest timestamp).

Net

The SDK is a CQRS/CRDT persistence core wearing a "sync engine" overcoat. The overcoat has no buttons: the provider contract is unimplemented, the resilience knobs (RetryConfig, RateLimitConfig, FetchConfig, IsRetryable) are inert, and the public Sync API actively conceals failure by always returning nil. Under real load against a real flaky provider, an operator will see items silently dropped, no retries, no rate-limit respect, and a green "no error" return.

5. The Boundary Question: Move to go-cqrs-lite?

User asked: "Maybe we actually just need to move some of the capabilities currently in this project to go-cqrs-lite or an existing or new sub module of it?"

What go-cqrs-lite IS

A 43-module CQRS + Event Sourcing library (v3.1.0) with per-module go.mod isolation. It provides the complete CQRS/ES primitive set — but deliberately excludes all distributed-systems sync primitives. Its authoritative charter doc (docs/ECOSYSTEM_BOUNDARIES.md) explicitly assigns CRDT/conflict logic to go-localsync, out of cqrs-lite.

The key insight: pkg/crdt/ is two unrelated things wearing one name

That conflation is the whole source of confusion:

Cluster A Generic conflict resolution

Conflict[T], ConflictResolver[T], LWWResolver[T]

A plain strategy pattern: "two candidate values arrive for one aggregate, which wins?" Generic over T. Not a CRDT — LWWResolver is literally "compare two timestamps." Every event-sourced app needs this policy.

Genuinely used

Cluster B Distributed delta-CRDT sync

VectorClock, Operation[T], SyncMessage, SyncRequest, SyncResponse[T]

Multi-node delta-exchange protocol types. Real CRDTs. Useful only when ≥2 nodes exchange deltas. Zero non-test references anywhere in the codebase.

Dead

The recommended three-way split

1. Conflict[T] / ConflictResolver[T] / LWWResolver[T] → new go-cqrs-lite/conflict/v3

The only migration that creates real value. Every event-sourced app needs a "what wins on conflicting writes" policy; today go-cqrs-lite's sole answer is "reject with a Conflict error and let the caller retry." A resolve/merge strategy fills a genuine gap. ConflictResolver[T] isn't a CRDT — so it doesn't violate the charter. Amend the boundary doc: generic conflict resolution IN, distributed CRDT merge OUT.

2. VectorClock / Operation[T] / SyncMessage / SyncRequest / SyncResponse[T] → delete (or defer)

This recommendation was later challenged — see §6. Moving dead code to a new home doesn't make it alive — it just relocates the facade. If/when a second node exists, revive into a correctly-named go-crdt-lite.

3. The model.Item-coupled half of pkg/cqrs/ stays

It's the domain. The generic wiring helpers (stack.go, store_factory.go) could eventually graduate to go-cqrs-lite/stack once de-domain-ified — but not worth the cost now.

Crucial caveat

Don't let "move things to cqrs-lite" become a way to avoid fixing the bleeding. Migration is orthogonal to the data-integrity bugs. The aggregate-ID collision, the hasChanged data loss, the lying Sync() — those stay broken regardless of where the types live.

6. Vector Clocks: A Defense, Then a Retraction

User pushed back: "VectorClock's sound cool though, and can solve real problems specially in cases where some emitter may not have internet for a while."

First response: a defense (partially correct, partially overreaching)

The initial reaction conceded that vector clocks aren't speculative — they earn their keep the moment an aggregate has ≥2 potential writers. The claim was that stack.DeleteItem was already a second writer (local delete vs remote update), making vector clocks the principled fix for a real present-day bug (silent resurrect-stale).

The scenario table

Scenario Does LWW lose data? Do vector clocks fix it?
Provider re-sorts/updates a live item No (one writer) No-op (correct)
Local delete + remote update interleave Yes Yes
Offline emitter buffers edits, reconnects Yes (concurrent updates) Yes
Multi-source merge of cross-posted items Yes (different provider clocks) Yes — only if items unify into one aggregate

The honest problem isn't the types — it's the empty wiring

The types are correct. VectorClock, Operation[T] are textbook-correct, well-tested primitives. Not theater. The lie is the empty construction in the decider — crdt.NewVectorClock() on every conflict, which makes the causal branch structurally unreachable while pretending it was consulted. So "delete the cluster" was the wrong prescription. The right one: keep the types, kill the empty-wiring, and decide whether to wire them for real.

Then: the retraction (see next section)

This entire defense rested on stack.DeleteItem being a live second writer. The next question exposed that assumption as false.

7. The DeleteItem Discovery: The Real Fork

User's two-word reaction to the stack.DeleteItem claim: "We have Delete?"

Verified against the code: DeleteItem exists at stack.go:154-166. But who calls it?

Surface Calls DeleteItem?
pkg/api/ (HTTP server) No
pkg/sync/ (sync loop) No
cmd/ No
Tests Yes — 8 test files

Full retraction of the vector-clock defense

If DeleteItem is never called outside tests, there is no second writer. The provider is the sole writer to every aggregate. Which means:

  • The resurrect bug (local delete vs remote update interleave) cannot occur in the running system — nothing writes the delete.
  • Vector clocks genuinely have no live justification today.
  • Pure LWW-by-timestamp is, for the actual current single-writer model, a defensible strategy — the problem was the empty vector-clock construction pretending it was consulted, not the absence of vector clocks.

DeleteItem, RateLimitConfig, RetryConfig, crdt.SyncMessage: all the same disease — implemented, unit-tested surfaces with no caller in the live system.

The real diagnosis

DeleteItem being orphaned means go-localsync hasn't decided what it is. The code today is neither a pure pull mirror nor a two-way sync engine — it's a pull mirror wearing a few of two-way-sync's clothes (DeleteItem, vector clocks, SyncRequest) with none of them wired. That's the source of the "dogshit" feeling — it's not under-built, it's uncommitted.

8. The Open Fork: What Is go-localsync?

This is the single product-identity decision that shapes everything downstream. Nothing else can be decided until it is.

⏳ DECISION REQUIRED: A or B?

One sentence settles the architecture. Everything in this document hangs off it.

Option A Pure pull mirror

Read-only local projection of upstream. SDK only ever adds/updates from provider. Deletion = "provider stopped returning it" → reconciliation diff, not an event.

  • DeleteItem → delete the orphan — misleading phantom surface.
  • Vector clocks → dormant / honestly stubbed. Single writer doesn't need them.
  • Upstream deletion → set-diff reconciliation.

Result: honest, tiny surface, vector clocks correctly absent rather than decorative.

Option B Offline-capable two-way sync

Local mutations (delete/edit) buffer and reconcile with upstream later. "Emitter loses internet" is a real scenario. DeleteItem is the seed of the real product.

  • DeleteItem → wire it to the API + sync loop as the first real local mutation.
  • Vector clocks / HLC → actually populate them. Eat the schema migration.
  • Much bigger scope — but it's a real product.

Result: causal history tracked, offline edits reconcile correctly.

Why this can't be deferred

Every other question in this document is downstream of A vs B:

  • Fix order: Both options require fixing the bleeding (aggregate-ID collision, hasChanged, lying Sync()) first. But only B then requires wiring DeleteItem + causality tracking.
  • Migration scope: Both options benefit from moving ConflictResolver[T] to go-cqrs-lite/conflict/v3. But only B keeps the distributed-CRDT cluster; A deletes it.
  • Resurrect handling: Under A, the resurrect bug is moot (no delete path). Under B, it's a real bug that vector clocks / HLC fix correctly.
  • Marketing honesty: Under A, "pull mirror" is honest. Under B, "two-way offline sync" must become true, not aspirational.

Recommended sequence (regardless of A or B)

  1. Fix the bleeding first — aggregate-ID collision, hasChanged content-hash, lying Sync() → real per-item errors. Pure localsync, no migration dependency.
  2. Decide A vs B. This is the pivot.
  3. Then: migrate ConflictResolver[T] → go-cqrs-lite/conflict/v3 (small, decoupling, unblocks reuse); and either delete the dead CRDT cluster (A) or wire causality for real (B).

The honest summary

The CQRS persistence core is genuinely good. The sync engine draped over it is uncommitted. The path to "superb" is not adding features — it's fixing the silent-data-loss paths, killing the phantom surfaces, and committing to one identity. The energy is right. The foundation, once the bleeding stops, is worth building on. But the A-vs-B question must be answered before a single line of new code is written, because it determines whether DeleteItem, vector clocks, and the entire offline story are the future of the product or scaffolding to tear out.
