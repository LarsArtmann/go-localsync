01Fully Done

Features that are implemented, tested, and production-ready.

+
CQRS event-sourced architecture Full Decider + ReadModel + Projector + EventStore via go-cqrs-lite v3.0. No legacy CRUD path. 3 domain events (ItemSynced, ItemConflictFound, ItemDeleted). pkg/cqrs — 89 tests, 81.4% coverage.
+
Deterministic aggregate IDs SHA256→hex from (source, sourceID) with sync.Map cache. Same inputs always produce the same ID. Idempotent sync: same item synced twice → 1 aggregate.
+
Pluggable conflict resolution CQRSConfig.ConflictResolver accepts any crdt.ConflictResolver[*model.Item]. Default nil = remote-wins LWW. DecideSync is the single authority — no split-brain. Winner constants exported with ParseConflictWinner.
+
CRDT primitives pkg/crdt ships VectorClock, Operation[T], Conflict[T], LWWResolver[T], SyncMessage. 53 tests, 96.2% coverage.
+
Dual storage backends In-memory (testing/dev) + SQLite (production) via modernc.org/sqlite (pure-Go, no CGo). Backend selected at construction via CQRSConfig.Backend. SQL snapshots cap replay cost.
+
Projection (live + replay) Direct bus.SubscribeAll for synchronous live delivery (read-your-writes). Background replayJournal for SQLite catch-up. Idempotent projection tolerates replay/live overlap — no checkpoint store needed.
+
Branded phantom-type IDs 6 types via go-branded-id: ItemID (ULID), ExternalID, ProviderID, ActorLogin, RepoID, EventTypeID. Compile-time type safety. pkg/id — 100% coverage.
+
HTTP API Huma v2 with GET /items, GET /stats, POST /sync, GET /health. OpenAPI 3 spec auto-generated. pkg/api — 14 tests, 94% coverage.
+
Error taxonomy go-error-family constructors (Rejection, Transient, Infrastructure) with intrinsic classification and IsRetryable. RegisterErrorTemplates() for all error codes with What/Why/Fix/WayOut. pkg/errors — 100% coverage.
+
Pure contract library All provider implementations + example CLI removed. SDK defines the Provider interface only. Reference consumer lives in github-local-sync. Clean architectural boundary.
+
DTO/domain boundary item_adapter.go converts provider.Item (DTO) → model.Item (domain entity with SchemaVersion). Decider, read model, events, and resolver all operate on *model.Item.
+
Sync engine Full sync, incremental sync, conflict-aware sync with progress callbacks. SyncStore interface decouples sync logic from CQRS infrastructure. pkg/sync — 24 tests, 85.5% coverage.
+
Nix flake + buildflow flake.nix with devShell + buildGoModule (vendored private deps). Buildflow pre-commit passes 26 checks (golangci-lint, gitleaks, nix-fmt, etc.). Version coherent at 0.3.0.
+
Schema versioning pkg/data/schema — Version (V1/V2) with CurrentVersion(), Valid(). Carried on every item for forward event migration (upcasting). 100% coverage.

02Partially Done

Implemented but with known gaps or incomplete coverage.

pkg/cqrs coverage at 81.4%

Lowest-coverage package. The core CQRS stack works correctly, but some error paths and store-factory branches lack test coverage. Target: 90%+.

Gap Error paths in store_factory.go, edge cases in snapshot loading, and some SQLite read model filter combinations.

CI pipeline — test + lint pass, build + release broken

The test and lint jobs in .github/workflows/ci.yml pass cleanly. The build job cross-compiles ./cmd/examples/github-sync — a path deleted when the SDK became a pure contract library. The release job depends on build, so neither runs.

Impact Tagged releases (like v0.3.0) trigger the release job, which fails. The GitHub Release must be created manually or the jobs must be reworked.

HTTP API — no auth, no rate limiting, no pagination headers

The API works correctly but has no production hardening: unauthenticated endpoints, no X-Total-Count pagination header, no rate limiting on POST /sync.

Vendored private dependency

go-cqrs-lite is private, forcing a committed vendor/ dir + vendorHash = null in flake.nix. Works, but prevents nix flake check from using a real vendorHash. Also bloats the repo with ~173 files of vendored deps.

04Broken / Fucked Up

Broken

CI build & release jobs cross-compile a deleted path

.github/workflows/ci.yml — build + release jobs

The build job runs go build ... ./cmd/examples/github-sync — a directory deleted in v0.2.0 when the SDK became a pure contract library. The release job depends on build, so neither job can succeed. Every tagged release (including v0.3.0) triggers a failing release job.

Fix A pure Go library has no binary to cross-compile. Either (a) remove both jobs entirely, (b) replace with a go build ./... smoke test, or (c) adopt a library-appropriate release flow. This is the #1 blocker for CI green.

05What to Improve

Architectural strengths to preserve

The CQRS-first design, SyncStore interface seam, branded IDs, and DTO/domain boundary are well-executed. The decider-as-single-authority for conflict detection eliminates split-brain. These are the foundations to build on.

Release automation gap

v0.3.0 was cut manually: changelog updated, commit amended, tag force-pushed. The CI release job that should automate this is broken. A library release flow (GoReleaser or GitHub-native) would make releases repeatable and less error-prone.

Observability blind spot

No tracing, no metrics. go-cqrs-lite v3 already ships an otel/v3 module — the wiring is available but unused. Production debugging currently requires log spelunking. This is the highest-impact gap for operational readiness.

Vendored dependency debt

The committed vendor/ dir (~34,000+ lines across 173 files) exists only because go-cqrs-lite is private. Making it public eliminates the workaround, shrinks the repo dramatically, and enables a real vendorHash for reproducible nix builds.

API production-readiness

The HTTP API is functional but unauthenticated, unrated, and lacks pagination metadata. Before any production deployment, auth + rate limiting + pagination headers are mandatory.

Test coverage depth

Overall coverage is strong (91.6% avg), but pkg/cqrs at 81.4% drags the average down. Focusing on error paths and store-factory branches would push the weakest package to 90%+.

07Top Open Question

Decision needed

What does a tagged release of a pure Go library look like without a binary?

.github/workflows/ci.yml — release job

The CI build and release jobs were written when the SDK shipped a CLI binary (gh-sync). That binary now lives in the consumer app github-local-sync. The SDK is a pure library — it has no binary to cross-compile, no artifact to upload, no release attachment.

Three options:

  • (a) Remove both jobs — the test + lint jobs already gate merges. A tag is just a git annotation, no CI artifact needed. Simplest.
  • (b) Replace build with a smoke test — go build ./... as a compile check, remove the release job entirely. Slightly more verification, no artifact.
  • (c) Keep a release job for GitHub Release notes — use softprops/action-gh-release with generate_release_notes: true and no binary artifacts. Creates a Release page from the CHANGELOG, even without a binary. Best DX for consumers browsing releases.
Why I can't decide this alone This is a product/UX decision: does a go-localsync consumer benefit from a GitHub Release page (option c), or is a git tag + CHANGELOG sufficient (option a/b)? The answer depends on how you want consumers to discover and track SDK releases. I recommend option (c) — Release notes are useful even for libraries, and the job is trivial to maintain.
