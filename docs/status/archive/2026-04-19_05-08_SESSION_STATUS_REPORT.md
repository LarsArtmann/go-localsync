**Key design decision needed for `sqlite.go`:** The 17 sites use double `%w` wrapping:

```go
fmt.Errorf("%w: get item by ID %q: %w", pkgerrors.ErrDatabase, id, err)
```

3. Use `errors.CombineErrors` (cockroachdb has this)

## E) WHAT WE SHOULD IMPROVE 🎯

### Process Improvements

1. **Stop running `go clean -cache`** — it destroys build performance for 10+ minutes. Only use as last resort.
2. **Use targeted builds** — `go build ./pkg/sync/` is fast; only run `go build ./...` before commits.
3. **Commit faster** — The sync.go changes are code-complete. Should have committed with just targeted package verification.

### Code Quality Improvements

1. **The vector clock system is decorative** — It resets on every restart, making conflict detection across sessions impossible. It adds ~50 lines of complexity for zero runtime value. Should be removed or properly persisted.
2. **Duplicate mocks** — `sync_test.go` has unexported `mockStorage`/`mockProvider` that duplicate `testhelpers.MockStorage`/`MockProvider`. They should be consolidated.
3. **`sqlite.go` error wrapping** — The double-`%w` pattern works but is fragile. Should decide on a consistent approach.
4. **Storage interface uses raw strings** — 7 methods take `string` params where branded types exist. This defeats the purpose of having branded types.

### Architecture Improvements

1. **Consider `SourceType` branded type** — `FetchOptions.Source` and `SyncOptions.Source` are both `string`. A branded `SourceType` would prevent mixing up source identifiers with other strings.
2. **Migration SQL embedding** — Currently string constants in Go. `embed.FS` would be cleaner and allow SQL tooling to work with the files.
3. **Error wrapping consistency** — 37 remaining `fmt.Errorf` sites (excluding sqlc-generated) need migration. The `pkg/errors` package is ready, just needs systematic application.

## G) Top #1 Question I Cannot Figure Out Myself 🤔

**Should we remove the vector clock system entirely (Option A), or persist it properly (Option B)?**

Current state: The vector clock in `ConflictAwareSyncer` is `localsync.NewVectorClock()` — an in-memory struct that **resets to empty on every process restart**. This means:

- Clocks are always `{}`
- `isConflict()` compares empty clocks → always falls through to LWW timestamp comparison
- The clock `Increment()` calls do nothing meaningful across restarts
- ~50 lines of code add zero runtime value

**Option A: Remove entirely** (recommended in original audit)

- Simpler code, less confusion
- Conflict resolution already works via LWW timestamps
- Removes dependency on vector clock API surface

**Option B: Persist properly**

- Would require serializing vector clock state to SQLite
- Adds complexity, storage schema changes
- Only valuable for multi-device sync (not current use case)

**I recommend Option A.** The vector clocks are decorative. Removing them simplifies the codebase without losing any actual functionality. But this is an architectural decision that could affect future plans I'm not aware of.
