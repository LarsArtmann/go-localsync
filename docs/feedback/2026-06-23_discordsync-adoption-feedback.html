What go-localsync would need to change before DiscordSync could consider it

An honest, grounded review of go-localsync's current architecture against DiscordSync's actual domain. The goal is not to dismiss the SDK — it has improved meaningfully — but to name precisely what blocks adoption, and what a generic multi-aggregate rewrite would look like.

00Summary

go-localsync is now a genuinely well-engineered single-aggregate sync SDK. Its CQRS stack, idempotent sync loop, deterministic IDs, and pluggable CRDT resolution are excellent — for the domain it models: paginated pull of flat items from one REST source into one event-sourced read model. DiscordSync's domain is structurally different: a push-driven stream (Discord Gateway) producing six aggregate types with thirteen typed events and four+ projections, each with rich typed payloads (attachments, embeds, edit history, soft-delete).

The bottom line go-localsync cannot host DiscordSync's domain without a fundamental rewrite of its core: the single hard-coded aggregate type, the fixed three-event vocabulary, the flat single projection, and the pull-only ingestion model. Tweaks won't close the gap. Both projects already correctly share go-cqrs-lite v3 — that is the right sharing boundary today.

For adoption to become worth revisiting, go-localsync would need to generalise from a single-aggregate Item sync engine into a multi-aggregate event-sourcing framework where consumers register their own aggregates, events, projections, and ingestion sources. The six findings below name exactly what that entails.

♦What's already shared (and correct)

Before the gaps: both projects already sit on the right foundation. This is not accidental — it is the correct sharing boundary, and it is the reason the gaps below are about what go-localsync adds on top, not about the primitives.

DiscordSync & go-localsync ├── go-cqrs-lite/event/v3 Event types, Store, Bus, Journal, Projection ├── go-cqrs-lite/id/v3 AggregateID, CorrelationID, branded IDs ├── go-cqrs-lite/codec/v3 JSONCodec, DecodePayload[T] ├── go-cqrs-lite/storage/v3 SQLite event store ├── go-cqrs-lite/snapshot/v3 Snapshot store └── go-cqrs-lite/watermill/v3 In-process EventBus
Key insight The shared layer already exists. The question is whether go-localsync's opinionated layer on top (Item aggregate, Provider sync, CRDT) adds value for DiscordSync or actively fights its domain.

01What's genuinely good in go-localsync now

These improvements are real and worth acknowledging — they are why the question is worth revisiting at all rather than dismissing outright.

+
Clean CQRS layer on v3 Decider, ReadModel, Projection, Stack — no legacy CRUD, idempotent sync, deterministic SHA256(source, sourceID) IDs. The v3 migration is done properly.
+
DTO / domain boundary provider.Item (DTO) → model.Item (domain) via item_adapter.go. Separation of wire format from domain entity is the right pattern.
+
Pluggable CRDT conflict resolution Inject any ConflictResolver[*model.Item]; LWW is default. Real composability for the single-aggregate case.
+
225 tests, strong coverage 89 tests in pkg/cqrs alone (81.4%). Idempotency, concurrency, replay, correlation all covered.
+
Synchronous projection + journal replay Live events via bus.SubscribeAll; SQLite catch-up via background journal replay with no checkpoint store. Read-your-writes preserved.

02What must change for adoption

Six structural gaps, ordered by how fundamentally they block adoption. Each names the current state (with code references), why it fights DiscordSync's domain, and what would need to change.

Blocking · Architectural core

1. Single hard-coded aggregate type

pkg/cqrs/events.go:10 · pkg/cqrs/decider.go:17-19

The SDK is built around exactly one aggregate. The aggregate type is a package-level constant const aggregateType = "sync_item", and the single decider state is SyncItemState{Item *model.Item, Deleted bool}. Every synced entity collapses into one flat Item. There is no mechanism to register a second aggregate type. 

// The single aggregate state — there is no other
type SyncItemState struct {
    Item    *model.Item
    Deleted bool
}

DiscordSync has six aggregates with distinct lifecycles: Message (created → edited → soft-deleted), Thread (created → updated → archived), Member (joined → updated → left), plus Channel, Guild, and User. Collapsing them into one Item loses the type-level distinctions that make the domain tractable.

What must change The stack must become aggregate-pluggable: consumers register their own AggregateType + Decider[S] pairs, and the store/indexing must support multiple aggregate types simultaneously (it already does at the go-cqrs-lite level — go-localsync just doesn't expose it).
Blocking · Domain expressiveness

2. Fixed three-event vocabulary

pkg/cqrs/events.go:12-19 · pkg/cqrs/projection.go:28-29

The SDK defines exactly three event types — sync_item.synced, sync_item.conflict_found, sync_item.deleted — and the projector handles only those three in a hard-coded switch. There is no way for a consumer to add discord.message.created, discord.reaction.added, or any domain-specific event without forking the projector. 

// Fixed — consumers cannot extend this
const (
    EventItemSynced        event.Type = "sync_item.synced"
    EventItemConflictFound event.Type = "sync_item.conflict_found"
    EventItemDeleted       event.Type = "sync_item.deleted"
)

DiscordSync has thirteen typed events with distinct payloads: MessageCreated (with Attachments[] and Embeds[]), MessageUpdated (with AfterContent, edit tracking), ReactionAdded, MemberJoined, ThreadArchived, and so on. A flat synced event cannot represent edit history or soft-delete semantics without losing the typed payload that makes the projections correct.

What must change Event types and their payloads must be consumer-defined. The SDK should provide the machinery (event construction helpers, codec, bus subscription) and let consumers declare their own event.Type constants and typed payload structs — exactly as DiscordSync already does directly against go-cqrs-lite.
Blocking · Read model

3. Single flat projection / read model

pkg/cqrs/projection.go:24-44 · pkg/data/model/item.go:17-29

One projector ("sync_item_projection") upserts into one flat read model keyed by (source, source_id) with columns like actor_login, repo_name, repo_url. DiscordSync needs four+ projections with rich relational shape: a messages table with edit history, soft-delete columns, joined attachments and embeds; a reactions table; a members table; a threads table — each driven by different event types. 

// DiscordSync's typed payloads — not representable in one flat Item
type MessageCreatedPayload struct {
    Attachments []AttachmentPayload // file download side-effects
    Embeds      []EmbedPayload
    Author      UserPayload
    ...
}
What must change Support multiple consumer-defined projections, each subscribing to its own subset of event types and writing to its own typed schema. The SDK already uses go-cqrs-lite's event.Projection interface — expose a registry so consumers can attach N projections, not one.
Blocking · Ingestion model

4. Pull-only ingestion (Provider.Fetch pagination)

pkg/provider/provider.go:128-141 · pkg/sync/sync.go

The entire sync engine is pull-based: a Provider implements Fetch() / FetchAll() with pagination, and the Syncer loops pages into the CQRS stack. DiscordSync's primary path is push: a persistent Discord Gateway websocket that delivers events as they happen. Backfill (REST pagination) is a secondary concern, and even it needs the fetched data routed into typed projections, not a flat Item table.

Provider.Fetch() → pages → flat Item vs Gateway WS push → typed events → N projections
What must change Decouple ingestion from the CQRS write path. The SDK should accept events from any source — a push handler, a webhook, a cron, or a paginated pull — and route them through consumer-defined command/event paths. The Provider + Syncer loop would become one optional ingestion adapter, not the only entry point.
Important · Domain leakage

5. The vocabulary is GitHub-shaped, not generic

pkg/data/model/item.go:17-29 · pkg/id/ids.go:19-52

Despite the "any provider" framing, the core types bake in GitHub's domain. model.Item carries ActorLogin, RepoName, RepoURL. The branded IDs include ActorLogin and RepoID. These fields have no Discord meaning — Discord has channels, guilds, authors, attachments, not repos and actors. An SDK named "localsync" that claims provider-agnosticism but ships repo-name columns signals the abstraction was extracted from one consumer, not designed from the domain. 

// model.Item — GitHub activity feed, not a generic sync entity
type Item struct {
    ActorLogin id.ActorLogin   // GitHub user
    RepoName   id.RepoID       // "owner/repo"
    RepoURL    string
    ...
}
What must change The domain model must either be truly generic (identity + timestamps + opaque typed payload, no provider-specific fields) or — better — consumer-defined entirely. The reference consumer (github-local-sync) would define ActorLogin/RepoID in its own package; the SDK ships only the sync/CQRS machinery.
Important · Query surface

6. Read model query surface is too narrow

pkg/data/model/item.go:47-52 · pkg/cqrs/readmodel.go

The read-side contract (ItemReader) exposes List, Count, CountByType, GetTypes — a flat-item query API. DiscordSync's Database interface has 28 methods: GetMessagesByChannel, paginated message search, attachment record updates after download, edit-history queries, member lookups by guild, thread archive filters, and stats aggregations. These are not variations on "list items"; they are genuinely different query shapes against a relational schema.

What must change The SDK cannot predefine the query surface. Consumers must own their read-model schema and queries. The SDK's value would be in the write-side machinery (event store, bus, projection wiring, idempotency) — not in a read-model contract that assumes one flat table.

03The target shape

If go-localsync were generalised to address all six findings, it would stop being an "Item sync engine" and become a multi-aggregate event-sourcing framework. The consumer (DiscordSync) would bring its own aggregates, events, projections, and ingestion, and the framework would provide the wiring.

Today — go-localsync
Target — generic framework
// Single aggregate, hard-coded
const aggregateType = "sync_item"

// Three fixed events
EventItemSynced, EventItemDeleted,
EventItemConflictFound

// One projection, flat read model
newProjector(rm)

// Pull-only: Provider.Fetch loop
NewSyncer(provider, stack, nil)
// Consumer registers N aggregates
stack.RegisterAggregate(
    msg.AggregateMessage,
    msg.Decider{},
)

// Consumer defines own event types
const MessageCreated event.Type = ...

// N projections, each its own schema
stack.AttachProjection(msg.NewProjection(db))

// Ingestion-agnostic: push OR pull
stack.Emit(ctx, evt) // from anywhere
The honest tradeoff At that point the framework's value-add over using go-cqrs-lite directly narrows to: projection wiring helpers, idempotency patterns, the CRDT conflict layer, and the optional Provider+Syncer pull adapter. That is still real value — but it must justify itself against the simplicity of the direct go-cqrs-lite path DiscordSync already uses successfully.

04Priority matrix

If go-localsync wanted to make itself viable for DiscordSync-class consumers, here is the order that unlocks the most per unit of effort.

The compounding effect Findings 1–4 are individually blocking and collectively reinforcing: fixing any one without the others still leaves a single-aggregate or single-projection straitjacket. They must be addressed together for the framework to cross the viability line — which is why this is a "fundamental rewrite," not an incremental enhancement.

What did improve (credit where due)

The correctness work materially improved the SDK's reliability for its actual consumers (github-local-sync). The projection race fix and content-hash data-loss fix were real bugs that could have caused silent data corruption. The error-handling overhaul brought structured error families to the entire codebase. The projectionhost adoption with dead-letter queue made poison-message recovery production-grade.

This is good engineering — it just doesn't change the adoption calculus. The gaps are architectural, and architecture doesn't shift from bug fixes.

Updated recommendation The original recommendation stands: both projects share go-cqrs-lite v3 as their common foundation, which is the correct level of reuse. DiscordSync's push-first, multi-aggregate, multi-projection architecture is fundamentally different from go-localsync's pull-only, single-aggregate, flat-read-model design. Convergence would require a rewrite of go-localsync's core — which the commit history shows no movement toward.
