Critical Fixes

Correctness issues that can cause silent data loss or inconsistent behavior in production.

LS-1

SyncItems bypasses the command middleware pipeline

Correctness

SyncItems (the primary write path for batch syncs) calls Repo.Execute() directly with a countingDecide closure — completely bypassing the CommandDispatcher. This means no logging, no validation, no retry, and no idempotency protection for the most important code path. Meanwhile, DeleteItem correctly dispatches through CommandDispatcher. This is an inconsistency that also loses observability.

pkg/cqrs/stack.go :165–243 pkg/cqrs/stack.go :189 (countingDecide) pkg/cqrs/stack.go :214 (Repo.Execute) pkg/cqrs/stack.go :157 (DeleteItem — correct path)
SyncItems() → Repo.Execute() — no middleware —
DeleteItem() → CommandDispatcher.Dispatch() → middleware chain → Repo.Execute()
1

Add SyncItemCommand dispatch for single items. Refactor SyncItem() to construct a SyncItemCommand with the deterministic aggregate ID pre-computed from AggregateID(source, externalID), then dispatch through CommandDispatcher. The handler already exists (handleSyncItem at commands_queries.go:185).

2

Refactor SyncItems to dispatch per-item. Loop over items, construct SyncItemCommand for each, dispatch through the pipeline. Capture results in a slice. The countingDecide hack goes away — domain semantics (created/updated/conflict) are determined from the decider's event output, which can be inspected via a post-commit hook or a result channel on the repository.

3

Resolve the DecideFunc return-type limitation upstream. The root cause is that DecideFunc returns ([]Event, error) with no way to carry domain metadata. File an issue / PR on go-cqrs-lite to extend the return type to a DecideResult struct that carries events + annotations. This eliminates reverse-engineering intent from event counts.

Impact
All batch syncs

LS-2

Type Safety

2

Verify all SyncStore methods are present. Check that SyncItems, ListItems, CountItems, GetItemTypes, Count, Close all match the interface. The duplicate GetTypes / GetItemTypes methods (see LS-6) should be resolved first.

Structural Improvements

Architectural patterns that are correct in spirit but have implementation gaps worth closing.

LS-3

CRDT infrastructure is overbuilt for current usage

YAGNI

pkg/crdt/ defines a full distributed sync protocol: VectorClock, Operation[T], SyncMessage, SyncRequest, SyncResponse[T], NodeID, OperationID. However, only ConflictResolver[T] and LWWResolver[T] are actually used. Vector clocks are always empty (created via crdt.NewVectorClock() and never populated). The remaining types are dead code adding cognitive overhead and maintenance surface.

pkg/crdt/conflict.go :ConflictResolver pkg/cqrs/decider.go :164–165 (empty vector clocks) pkg/crdt/operation.go :Operation[T] (unused) pkg/crdt/vectorclock.go :VectorClock (always empty)
1

Keep the conflict resolution types. Conflict[T], ConflictResolver[T], LWWResolver[T] are actively used and well-designed. Leave them in pkg/crdt/.

2

Document the unused types as future API. Add a doc.go to pkg/crdt/ explaining which types are active vs. planned-for-later. This avoids confusion for new contributors without deleting code that has a clear future purpose.

3

Add tests for empty-vector-clock behavior. If the contract is "empty clocks mean LWW falls through to timestamp," encode that in a test. This documents the behavior and catches regressions.

ℹ The types aren't wrong — they're well-designed for a future multi-node sync story. The issue is that they're undocumented dead weight right now. A doc comment + test is cheaper than deletion + re-creation later.

LS-4

Inconsistent not-found semantics across ReadModel implementations

Correctness

MemoryReadModel.Get() returns (nil, nil) for missing items. SQLiteReadModel.Get() returns (nil, ErrNotFound). This semantic mismatch means code that works in development (memory backend) breaks in production (SQLite backend) or vice versa. Callers can't write consistent error-handling code.

pkg/cqrs/memory_readmodel.go :27 (returns nil, nil) pkg/cqrs/sqlite_readmodel.go :64 (returns nil, ErrNotFound) pkg/cqrs/readmodel.go :13 (interface)
Before
// MemoryReadModel — silent nil
func (m *MemoryReadModel) Get(...) (*model.Item, error) {
  return nil, nil  // ← ambiguous
}
After
// MemoryReadModel — explicit ErrNotFound
func (m *MemoryReadModel) Get(...) (*model.Item, error) {
  item, ok := m.items[key]
  if !ok {
    return nil, pkgerrors.ErrNotFound
  }
  return item, nil
}

LS-7

SQLite read model never persists raw JSON

Data Loss

SQLiteReadModel.Upsert() always stores []byte{} for the raw_json column. The actual raw JSON lives only in the event payload. The scannedItem.rawJSON field is scanned from the column but never used. This is a dead column + dead field — wasted storage and confusing code.

pkg/cqrs/sqlite_readmodel.go :157 (empty raw_json) pkg/cqrs/sqlite_readmodel.go :247–288 (scannedItem dead field) pkg/cqrs/item_adapter.go :57 (ToItemView unused rawJSON param)
1

Option A: Persist raw JSON. Thread the rawJSON []byte through the projection path (handleItemSynced → ReadModel.Upsert). Requires extending ReadModel.Upsert signature or adding the raw JSON to model.Item.

2

Option B: Remove the column. If raw JSON is only needed from events (replayable), drop the raw_json column from the DDL, the scannedItem.rawJSON field, and the unused ToItemView parameter. Cleaner — raw JSON is an event-store concern, not a read-model concern.

ℹ Recommendation: Option B. The read model should contain the denormalized query fields, not the raw provider payload. Raw JSON belongs in the event store. If consumers need it, they can replay events.

Appendix A: Generics Opportunities

Where Go generics can eliminate boilerplate, replace runtime assertions with compile-time checks, and make the codebase more robust. Ordered by impact.

G-1

Adopt command.RegisterTyped[C] for all command handlers

Boilerplate

The query package already has RegisterTyped[Q, R] and DispatchTyped[T] — the "typed bookend" pattern that eliminates runtime type assertions. But command has no equivalent. Meanwhile, go-localsync doesn't use query.RegisterTyped either — all 6 handlers (2 command + 4 query) use raw Register with manual type assertions. This creates 6 identical blocks of assertion + error-wrapping boilerplate.

pkg/cqrs/commands_queries.go :189–213 (command handlers) pkg/cqrs/commands_queries.go :239–281 (query handlers) go-cqrs-lite/query/dispatcher.go :77 (RegisterTyped — exists but unused) go-cqrs-lite/command/dispatcher.go :— (no RegisterTyped)
Current — 6× repeated
func handleSyncItem(repo, resolver) command.Handler {
  return func(ctx context.Context, cmd command.Command) error {
    syncCmd, ok := cmd.(*SyncItemCommand)
    if !ok {
      return fmt.Errorf(
        "expected *SyncItemCommand, got %T: %w",
        cmd, errCommandTypeMismatch)
    }
    return repo.Execute(ctx, syncCmd.AggregateID(),
      aggregateType, DecideSync(syncCmd.Item, ...))
  }
}
With RegisterTyped — zero assertions 
// go-cqrs-lite adds (upstream CQ-8):
func command.RegisterTyped[C Command](
  d *Dispatcher, t Type,
  h func(ctx context.Context, cmd C) error,
) error

// go-localsync wiring becomes:
command.RegisterTyped[*SyncItemCommand](
  dispatcher, commandTypeSyncItem,
  func(ctx context.Context, c *SyncItemCommand) error {
    return repo.Execute(ctx, c.AggregateID(),
      aggregateType, DecideSync(c.Item, ...))
  },
)
1

Upstream: add command.RegisterTyped[C] to go-cqrs-lite. Mirrors the existing query.RegisterTyped[Q, R] pattern. The assertion moves inside the library where it's tested once, not repeated in every consumer.

2

Consumer: adopt RegisterTyped for all 4 query handlers. This requires no upstream changes — query.RegisterTyped already exists. Just not used. Deletes ~40 lines of assertion boilerplate immediately.

3

Consumer: adopt command.RegisterTyped for both command handlers once upstream ships it. Deletes ~20 more lines. The errCommandTypeMismatch sentinel error and all ok checks disappear entirely.

Quick win: Step 2 requires zero upstream changes. The query.RegisterTyped function already exists in go-cqrs-lite v2.2.0 — go-localsync just doesn't use it. Adopting it for all 4 query handlers is a pure refactor that deletes ~40 lines today.

G-2

Typed DecideResult[R] instead of map[string]any

Type Safety

The CQ-1 proposal in the go-cqrs-lite plan suggests Annotations map[string]any for domain metadata. That's stringly-typed — consumers must assert annotation values at runtime. Generics give a better answer: a second type parameter on DecideFunc that carries a typed domain result through the library's own type system.

CQ-1 as proposed (stringly-typed) 
type DecideResult struct {
  Events     []event.Event
  Annotations map[string]any  ← runtime assertion
}

// Consumer must assert:
action := result.Annotations["action"].(string)
With generics (compile-time typed) 
type DecideResult[R any] struct {
  Events []event.Event
  Result R                   ← typed at compile time
}

type DecideFunc[S any, R any] func(
  state S, ver event.Version,
) (*DecideResult[R], error)

// Consumer gets typed result directly:
result.Action  // synclib.SyncAction — no assertion

go-localsync defines its domain result type: 

type SyncDecision struct {
  Action    synclib.SyncAction
  WasNew    bool
  Conflict  string
}

// DecideSync returns a typed result — no countingDecide hack:
func DecideSync(...) func(
  state SyncItemState, ver event.Version,
) (*decider.DecideResult[SyncDecision], error)
1

Upstream: parameterize DecideFunc with a result type. DecideFunc[S, R] where S is aggregate state and R is the domain result. Provide DecideFunc[S] as an alias for DecideFunc[S, struct{}] for consumers who don't need domain results.

2

Consumer: define SyncDecision and return it from DecideSync. The countingDecide closure in SyncItems is replaced by reading result.Action, result.WasNew, result.Conflict directly. No more reverse-engineering intent from event counts.

Tradeoff: Two-parameter generics (DecideFunc[S, R]) increase library complexity. For consumers who don't need domain results, the DecideFunc[S] alias keeps the simple case simple. The benefit is eliminating an entire class of bugs where domain semantics are guessed from event counts.

G-3

Rewrite Projector using projection.On[T] builder

Zero Library Changes

go-cqrs-lite's projection.On[T] already does typed payload decoding inside a wrapper — the exact pattern that go-localsync's Projector reimplements manually. Three handleXxx methods in projection.go each call event.DecodePayload[T] and then delegate to the read model. The builder eliminates all of this.

pkg/cqrs/projection.go :33–69 (3 manual handler methods) go-cqrs-lite/projection/builder.go :30 (On[T] — already exists)
Current — 3 manual methods 
func (p *Projector) Handle(ctx, evt) error {
  switch evt.Type() {
  case EventItemSynced:
    return p.handleItemSynced(ctx, evt)
  case EventItemDeleted:
    return p.handleItemDeleted(ctx, evt)
  case EventItemConflictFound:
    return nil // no-op
  }
}

func (p *Projector) handleItemSynced(ctx, evt) error {
  payload, err := event.DecodePayload[ItemSyncedPayload](
    evt, codec.JSONCodec{})
  if err != nil { return err }
  item, err := DataItemFromPayload(payload)
  if err != nil { return err }
  return p.readModel.Upsert(ctx, item)
}
With projection.On[T] builder 
builder := projection.NewBuilder("sync_item_projection")

projection.On[ItemSyncedPayload](
  builder, EventItemSynced, codec.JSONCodec{},
  func(ctx context.Context, p ItemSyncedPayload) error {
    item, err := DataItemFromPayload(p)
    if err != nil { return err }
    return rm.Upsert(ctx, item)
  },
)

projection.On[ItemDeletedPayload](
  builder, EventItemDeleted, codec.JSONCodec{},
  func(ctx context.Context, p ItemDeletedPayload) error {
    return rm.Delete(ctx, p.Source, p.ExternalID)

proj := builder.Build() // event.Projection
No upstream changes needed. projection.On[T] ships in go-cqrs-lite v2.2.0. This is a pure consumer-side refactor. The Projector struct and its 3 handler methods collapse into a builder call. The EventItemConflictFound no-op handler is simply omitted — the builder only registers event types that have handlers.

G-4

Generic ReadModel[T] for cross-domain reuse

Future · If Needed

The current ReadModel interface is hardcoded to *model.Item. If go-localsync adds a second aggregate type (notifications, webhook deliveries, audit logs), every read model implementation must be rewritten from scratch. A generic ReadModel[T] would allow the MemoryReadModel and SQLiteReadModel to be reused across domains. 

type ReadModel[T any] interface {
  Get(ctx context.Context, key string) (T, error)
  List(ctx context.Context, filter Filter) ([]T, error)
  Count(ctx context.Context, filter Filter) (int64, error)
  Upsert(ctx context.Context, item T) error
  Delete(ctx context.Context, key string) error
  Close() error
}
Only worth doing when there's a second consumer. Right now the provider.ItemFilter has specific fields (Type, Actor, Repo, Source, Since) that don't generalize. Genericizing the filter would force any — which is worse than the current domain-specific interface. Revisit when a second aggregate type is added.
