1 What did I forget?

The reconcile footgun is still armed

I added SyncOptions.Reconcile and documented it loudly, but I did not wire the one signal that already exists to protect it. provider.FetchResult.HasMore tells us whether pagination is exhausted, yet reconcile() (pkg/sync/sync.go) never reads it. A caller who sets Reconcile: true on a still-paginating fetch silently tombstones every not-yet-fetched item. The data to prevent this is right there — I just didn't connect it.

No example for the headline feature

The tombstone→resurrect loop is the SDK's most distinctive behavior, and I wrote a whole ADR about it — but pkg/cqrs/example_test.go only shows the happy-path sync. A reader who wants to see a tombstone come back to life has to read the test suite. The example undersells the product.

2 What's stupid that we do anyway?

pkg/sync named sync — collides with the stdlib

Every file in that package has to alias the standard library: stdsync "sync". I hit this exact footgun myself this session and spent a cycle on it. It is a self-inflicted wound baked into the import path. The fix (pkg/sync → pkg/synclib) is mechanical but breaking for the one consumer (github-local-sync), so I deferred it. That is the right call for now — but it stays on the list.

lockSource map grows forever

Syncer.locks map[string]*sync.Mutex adds an entry per source and never removes one. For a bounded source set (a few GitHub users) this is invisible. For dynamic/ephemeral sources it is an unbounded leak. Cheap to fix: clean the map (or keep the lock hot) on release.

3 What could I have done better?

I trusted a stale handoff note before checking the tree

The session reminder insisted the build was broken and uncommitted. A 5-second git status showed a clean tree with everything already in 8c0847f. I should have verified state first, always — the tree is the source of truth, never a summary of it.

Retry config is a sealed box

NewSyncer hard-codes provider.DefaultRetryConfig with no setter. The plumbing (RetryConfig{Enabled, MaxRetries, InitialBackoff, MaxBackoff}) is correctly honored — I verified fetchItems checks both Enabled and MaxRetries — but a consumer cannot reach it. For a "superb SDK" the caller must control backoff (a rate-limited GitHub mirror is not a LAN GitLab). This is the single highest-impact API gap.

4 Split brains (yes, two)

Two result types with overlapping semantics

sync.SyncResult has Fetched, Skipped, Tombstoned, Errors, ItemErrors. sync.ConflictResult has Fetched, Upserted, Skipped, Conflicts, Errors — and is missing Tombstoned and ItemErrors. The conflict-aware path silently drops the tombstone count and per-item error detail. That is a real inconsistency: two shapes describing the same operation, one of them lossy.

Status report said "2 commits" — I made 3

The report was drafted before I split the lint fix from the docs commit. A snapshot, so not worth re-writing, but it is a small honesty lapse worth noting: write the report after the final commit, or re-read it before pushing.

5 Scope creep & ghost systems

No ghost systems found

I verified every "suspicious" export: Syncer.Store() is used by the API server; Stats/GetStats feeds the /stats handler; SyncSummary is the SyncStore.SyncItems contract; ActionUnchanged/ActionError are emitted by the stack adapter and validated by IsValid(). pkg/testutil is heavily used across both test suites. Nothing is dead.

The CRDT cleanup was real

Removing VectorClock/Operation/SyncMessage was correct — they were genuinely dead code for a single-writer pull mirror, not deferred value. ADR-0003 now records the retirement honestly. No scope creep crept back in.

The retry/resurrect behaviors are well covered; the gap is the safety invariant I forgot to enforce.
