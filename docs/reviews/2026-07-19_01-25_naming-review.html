02Findings

Medium

SyncResult vs SyncSummary — sibling result types, non-aligned vocabularies

pkg/sync/sync.go:128 (SyncResult) · pkg/sync/types.go:41 (SyncSummary) · pkg/cqrs/sync_outcome.go:14 (SyncOutcome)

Three types summarize a sync's outcome at different layers. SyncResult (Syncer layer) uses Fetched/Skipped/Tombstoned/Errors/ItemErrors. SyncSummary (SyncStore layer) uses Synced/Conflicts/Errors/Results. SyncOutcome (decider layer) uses WasNew/ConflictDetected/ConflictWinner/EventCount. The layering is correct (each type lives where its layer needs it), but the two top-level count-vocabularies don't align: Fetched ≠ Synced, Skipped has no SyncSummary equivalent, Conflicts has no SyncResult equivalent. A newcomer cannot predict which counts appear where.

Recommendation (do not rush) This is a genuine layering seam, not a bug — the types are at different abstraction levels on purpose. If touched, align the count-field names across SyncResult and SyncSummary (e.g. both expose Synced/Conflicts/Skipped/Tombstoned/Errors), OR document the layer relationship explicitly in a doc comment. Renaming public fields is a breaking API change for a library — defer to a v0.5.0.
Low

Stats — vague noun for a read-model aggregate

pkg/sync/sync.go:137 · returned by Syncer.GetStats

The checklist flags Stats as carrying no domain meaning. It is contextually clear (Syncer.GetStats() → *Stats holds TotalItems/ItemTypes/TypeCounts), but ItemStats or ReadModelStats would be more precise and self-documenting at the type-signature level.

Low

GetStats — redundant Get prefix (Go idiom)

pkg/sync/sync.go:333

Go style (Effective Go, golint) prefers accessors without Get when there is no matching Set: syncer.Stats(ctx) over syncer.GetStats(ctx). Debatable — many Go codebases keep Get for clarity — but flagging for consistency with Go conventions. No Set* counterpart exists.
