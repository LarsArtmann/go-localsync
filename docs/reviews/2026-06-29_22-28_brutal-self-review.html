The 11 Questions — Answered Honestly

FOUND

1. What did you forget?

The projection's version gate (projection.go:43-69) uses two separate sync.Map ops — Load to check, Store after applying. That is a classic check-then-act race: a stale journal-replay event (v1) can pass the gate between a live tombstone (v3) loading and storing, resurrecting a tombstoned row. Two sessions of "production-ready" review called the projection "idempotent" without noticing the gate isn't atomic.

FOUND

2. What is something stupid that we do?

NewCQRSStack has seven error-return sites after store+bus creation, none with cleanup. If the read-model migration, projection runner, snapshot store, or command dispatcher fails, the SQLite connection pool and the projection goroutine leak forever. It's the textbook "constructor without defer cleanup" anti-pattern. We also validate provider.Item without checking UpdatedAt — but model.Item.Validate() does require it, so a zero-UpdatedAt item sails through the entry filter only to poison its own aggregate on the next fold.

FOUND

3. What could you have done better?

Run the three-agent deep investigation with specific correctness mandates (not just "find ghosts"). This session's bug agent had a concurrency checklist and found the projection race in minutes. Prior sessions dispatched agents for ghosts and naming but never for races and resource leaks — which is exactly where the real damage hides.

THIS SESSION

4. What could you still improve?

MemoryReadModel returns/stores shared mutable pointers (no defensive copy — a real aliasing risk). The Since filter is inclusive in memory, exclusive in SQLite — switching backends silently changes boundary results. SQLite error wrapping uses fmt.Sprintf("…: %v", err) which severs the error chain — errors.Is / errors.As can never reach the root cause. All addressed this session or documented below.

HONEST

5. Did you lie to me?

Yes. Sessions 26-27 declared the projection "idempotent" and the codebase "production-ready." The projection race, the constructor leak, and the validation gap were all present then — I just didn't look for them. The honest line: "idempotent under sequential delivery, racy under concurrent live+replay." That's a material difference I glossed over twice.

LESSON

6. How can we be less stupid?

Mandate a dedicated concurrency + resource-leak investigation pass before any "production-ready" claim — separate from ghost-hunting and naming. Also: when a comment says "idempotent" or "tolerates overlap," write the test that proves it under concurrent delivery, not just sequential re-delivery.

27 FOUND

Yes — 27. The most impactful: ConflictAwareSyncer (entire file, zero production callers), Provider.Fetch() / FetchOptions / GetRateLimit() / RateLimitInfo (dead interface surface), the CQRSStack.conflictResolver field (set, never read), ActionTombstoned (defined, parsed, never produced), and 8 WithXxx() filter builders used only in their own test. Full list below.

FOCUSED

8. Scope creep?

Resisted it. The ExternalID↔SourceID naming duality and the source string → id.ProviderID widening both touch versioned event schemas or large public surfaces. They're real split brains but fixing them blindly risks data corruption. Deferred with explicit rationale.

N/A

9. Did we remove something useful?

Not yet this session — but the ghost cleanup (Step 8) removes ~20 methods/types/constants whose only callers were their own tests. Nothing production-facing is lost.

10 FOUND

10. Split brains?

Ten. The worst: SQLite silently drops ContentHash and SchemaVersion on every round-trip (no columns in the DDL). Two validation functions (provider.Item.Validate vs model.Item.Validate) check different fields and use different error conventions. Tombstone reconstruction is copy-pasted between decider and projection. Full list below.

ADEQUATE

11. How are we doing on tests?

180 tests pass, race-clean. But every SQLite test uses :memory: with SetMaxOpenConns(1) — which serializes all queries and structurally hides concurrency bugs. The projection race would never reproduce under those tests. This session adds regression tests that target the concurrent paths explicitly.

Deliberate Deferrals

  1. ConflictAwareSyncer — zero production callers but provides a richer ConflictResult (per-item details) the base Syncer doesn't. Decision needed: integrate into base Syncer vs delete vs keep as opt-in. Has a latent bug (always returns nil error) that's moot if deleted.
  2. Provider interface pruning (Fetch/FetchOptions/GetRateLimit/RateLimitInfo) — public API change affecting every consumer implementor. Defer to a major-version bump.
  3. ExternalID ↔ SourceID naming unify — touches the versioned event JSON schema. Requires an upcasting migration.
  4. source string → id.ProviderID on 10+ function signatures — breaking change across cqrs/sync/provider. Defer.
  5. MemoryReadModel defensive copies — real aliasing risk but changes allocation profile. Needs a benchmark pass.
  6. Redundant tombstoned column — SQLite has both a boolean and a reason; the model uses only reason. Migration risk.
  7. OpenTelemetry wiring — decision made (consumer-wrap); sized follow-up.
  8. SQLite tests all use :memory: — structurally hides concurrency bugs. Add file-backed + WAL integration tests.
