go-cqrs-lite — Adoption & Utilization Audit

go-localsync is go-cqrs-lite's most deliberate consumer: a single-aggregate pull-mirror SDK built entirely on the library's event-sourcing core. This audit compares what the project uses against everything the library's 34-module monorepo offers. Verdict: the core engine usage is textbook — near-superb — with one real defect, three missed opportunity classes, and a handful of small hand-rolls the library has since absorbed.

00Summary

go-localsync consumes go-cqrs-lite exactly the way the library's README asks consumers to: as a library, not a framework. The decider pattern, typed command dispatch, snapshot integration, CBOR codec, managed projection hosting, and the deliberate avoidance of deprecated presets all reflect a project that understands the library's architecture — and documents its decisions in ADRs. Every one of the 12 direct module dependencies is pinned at the latest release.

The gaps are real but bounded. One is an outright defect: the projection dead-letter queue is in-memory while the event store is SQLite, so captured poison events vanish on restart (the library's own linter flags this as its only ERROR). The others are observability (no correlation IDs on single-item syncs, no telemetry hooks), an untouched testing toolkit (eventtest, scenario, testutil), and a few small hand-rolls (DeriveStreamID, validation middleware) that duplicate capabilities the library now ships.

The bottom line Nearly superb. Fix the DLQ volatility mismatch (one-line constructor swap), make correlation/causation metadata universal (a day of work), and wire the library's own cqrs-lint into CI — those three move this from "very good consumer" to "reference consumer."

01Current Usage

All library usage is concentrated in pkg/cqrs (11 production files), with the storage backends selected in store_factory.go and the projection wiring in runner.go. The stack is composed by hand in NewCQRSStack — deliberately, per ADR-0004's single-aggregate scope — rather than via the library's (deprecated) stack presets.

02Findings — gaps & defects

Ordered by impact. Every claim is cited to code or library source.

Misused · High impact

In-memory DLQ paired with a persistent event store

pkg/cqrs/runner.go:42 · flagged by cqrs-lint C017 (its only ERROR)

The projection host captures poison events into projectionhost.NewMemoryDeadLetterStore() — but with the SQLite backend the event store, checkpoints, and read model all survive restarts. A captured poison event is lost on restart, so after every crash the host re-reads the same poison event from the journal, fails 3 more times, and re-captures it. The DLQ's purpose — a durable quarantine for inspection — silently degrades to a per-process buffer.

Before — volatile
After — matches the store backend
host, err := projectionhost.New(
    sr.journal, sr.cpStore,
    projectionhost.WithLogger(newSlogLogger()),
    projectionhost.WithDeadLetterStore(
        projectionhost.NewMemoryDeadLetterStore(), 3),
)
// memory backend keeps the memory DLQ; sqlite gets:
dlq, err := projectionhost.NewSQLiteDeadLetterStore(ctx, db)
host, err := projectionhost.New(
    sr.journal, sr.cpStore,
    projectionhost.WithLogger(newSlogLogger()),
    projectionhost.WithDeadLetterStore(dlq, 3),
)
Fix In createStores' SQLite branch, construct projectionhost.NewSQLiteDeadLetterStore(ctx, db) (sqlite_dlq.go:83 — takes the already-open *sql.DB, creates its table idempotently) and thread it into the host alongside the checkpoint store. Keep the memory DLQ for the memory backend. Small test addition: assert the DLQ table survives a store reopen.
Partially Used · Medium impact

Correlation metadata covers only the batch path; causation is never recorded

pkg/cqrs/stack.go:193 (Options: nil) vs stack.go:270-288 · commands.go:77-83

SyncItems stamps every event with a per-run CorrelationID via event.WithCorrelationID — good. But SyncItem (single item) dispatches with Options: nil, and TombstoneItemCommand has no options field at all. Half the write paths emit events that cannot be tied to a run. Additionally, the library offers decider.WithEnricher (options.go:41) and command-causality tagging — every event could carry the causing command's ID for free, giving a complete command→event audit chain. Today no event carries a CausationID.

Recommendation Two moves: (1) give TombstoneItemCommand an Options field and default a fresh cqrsid.NewCorrelationID() in both single-item paths; (2) register the library's causality enricher once at repository construction so metadata enrichment stops being a per-call-site concern: 
repo, err := decider.NewRepository[SyncItemState](store, bus, d,
    decider.WithSnapshotStore(snapStore),
    decider.WithCodec(codec.CBORCodec{}),
    decider.WithSnapshotStrategy(snapshot.EveryNEvents(10)),
    decider.WithEnricher(event.CommandCausalityEnricher),
)
Missed Opportunity · Medium impact

The library's testing toolkit is completely untouched

not used anywhere · eventtest, scenario/v4, testutil/v4 exist only in go.sum

go-cqrs-lite ships a purpose-built test layer: eventtest (FakeStore/FakeBus/FakeSnapshotStore with fluent error injection, event factories, golden assertions), scenario (a BDD DSL for exactly the decider/projection tests pkg/cqrs writes), testutil (rapid property-based generators), and event.WithClock for deterministic timestamps. None of the 95 pkg/cqrs tests use any of it — every fixture is hand-rolled (mustNewTestEvent, waitForCount, state builders in testing_test.go:91-188). The library also documents its own fold-exhaustiveness concern (rule B005) which the custom fold already handles correctly by erroring on unknown types.

Recommendation Don't retrofit the passing suite. Adopt scenario for new decider specs — it maps 1:1 onto the existing test intent and enforces a terminal assertion: 
scenario.Given(t, fold, SyncItemState{},
    tombstonedSyncedEvent(t, item)).
    When(cmd, decideSync(item, raw, nil)).
    Then(EventItemSynced) // resurrection emits a sync event
Use eventtest.FakeStore where tests currently assert against real in-memory stores, and event.WithClock to make timestamp assertions deterministic instead of post-hoc range checks.
Missed Opportunity · Medium impact

No telemetry hooks despite the library being instrumented end-to-end

not used anywhere · otel/v4 is an indirect dep; middleware/projectionhost metrics unused

The library provides one-call observability: middleware.NewOTelBundle(tracer, meter) (otel_bundle.go:83) yields command/event/query/publish middleware plus a correlation enricher; projectionhost.WithMetrics(r) (metrics.go:42) exports lag and worker-state gauges; prometheus.Setup() bridges everything to /metrics. go-localsync — itself an SDK that consumers embed — exposes none of this: CQRSConfig has no telemetry surface, so consumers cannot observe sync latency, conflict rates, DLQ depth, or projection lag without forking.

Recommendation Add an optional CQRSConfig.OTel *middleware.OTelBundle (nil = today's zero-telemetry behavior). When set, apply bundle.Command()/bundle.Event() to the dispatchers and pass bundle.MetricsRecorder to projectionhost.WithMetrics. Purely additive; no default behavior change.
Missed Opportunity · Medium impact · trivial effort

The library's own cqrs-lint (203 rules) is not in CI

cmd/cqrs-lint in go-cqrs-lite · consumer-facing by design ("for go-cqrs-lite consumers")

go-localsync maintains its own internal/cqrslint (10 bespoke ADR-0004 invariants — good, keep it). But the library ships a domain-aware consumer linter that found, in this audit's run against pkg/cqrs (101 ms): the C017 DLQ error above, 8 ignored Close() errors, a time.Now() inside the decider, and a panic in a production path. Full results in the appendix. It runs read-only, emits SARIF/JSON, and its false positives (2 confirmed) are suppressible.

Recommendation Add a CI leg: go run github.com/larsartmann/go-cqrs-lite/cmd/cqrs-lint/v4@latest ./pkg/... --min-severity error (gate on errors only; let warnings report non-blocking). It complements internal/cqrslint: theirs checks library-consumer correctness, ours checks project architecture.
Partially Used · Low-medium impact

Hand-rolled validation middleware duplicates middleware.CommandValidation

pkg/cqrs/middleware.go:10-35 vs middleware/validation.go:49-63

The 25-line commandValidationMiddleware reimplements what the library already ships: middleware.CommandValidation(validator) takes a CommandValidator func(command.Command) error — the exact shape of the hand-rolled switch — and adds opt-in failure logging via middleware.WithLogger, which the hand-roll lacks (validation failures are currently silent).

Before — 25 lines, unlogged
After — library middleware
dispatcher.Use(commandValidationMiddleware())
// middleware.go:10-35, hand-rolled
dispatcher.Use(middleware.CommandValidation(
    validateSyncCommands,
    middleware.WithLogger(newSlogLogger()),
))
// validateSyncCommands = the same type switch, as a plain func
Partially Used · Low impact · migration-sensitive

AggregateID hand-rolls what id.DeriveStreamID now provides

pkg/cqrs/aggregate_id.go:17-52 vs id/stream_id.go:145, id/derive.go:14-24

The library's DeriveStreamID(namespace, keys...) is a namespaced SHA-256 (NUL-separated, collision-safe) — the same concept as the hand-rolled length-prefixed SHA-256[:16] + sync.Map cache. The hand-roll adds caching the library lacks, but encodes differently, so the two produce different stream IDs for the same item. Switching outright would orphan every existing event stream — this is a documentation decision, not a refactor.

Recommendation Keep the current derivation (data compatibility wins) but pin the divergence in a comment on AggregateID referencing id.DeriveStreamID, and consider upstream-contributing the sync.Map cache idea to the library's derive path.
Partially Used · Low impact

Schema evolution handled by "fat payload" instead of the Upcaster registry

pkg/cqrs/events.go:41-47 vs schema/upcaster.go (NewUpcaster, UpcastSourceTransform)

V1/V2→V3 (de-githubify, ADR-0007) compatibility is achieved by keeping four legacy fields in ItemSyncedPayload forever and upcasting in dataItemFromPayload. The library's schema module formalizes this: versioned Upcasters registered per event type, applied transparently at the store boundary via UpcastSourceTransform + event.DecorateStore. With exactly three event types and one historical migration already shipped, the fat payload is defensible — but a second schema change would make the upcaster pipeline the cheaper path.

Polish · Low impact

Hygiene cluster: time.Now in decider, panic fallback, ignored Close errors

decider.go:147 · aggregate_id.go:46 · stack.go:173-181, store_factory.go:58-78

Three small items surfaced by the lint run: TombstonedAt: unixNano(time.Now().UTC()) (decider.go:147) makes new-tombstone event payloads non-deterministic — inject a clock (the library's event.Clock pattern) or thread the timestamp from the command; the documented-unreachable panic (aggregate_id.go:46) could return an error now that AggregateID has a single call contract; and eight _ = x.Close() calls in shutdown paths swallow real close failures — log them (C023).

03Fully leveraged — done right

Fully Leveraged

The event-sourced core is used exactly as designed

decider.go · commands.go · stack.go · events.go

Pure fold with a strict default branch (unknown event types return a classified error, decider.go:53-61 — satisfying the library's B005 concern by hand), events built via event.NewEvents with the aggregate-type const (project lint C0010), payloads decoded via event.DecodePayloadAuto with zero manual json.Unmarshal in the decider path, and optimistic concurrency through repo.ExecuteRef alone. Conflict handling is a clean ConflictResolver seam with remote-wins default — a pattern the library explicitly leaves to consumers.

Fully Leveraged

Projection architecture matches the library's intended tier

runner.go · projection.go · ADR-0006

Live synchronous delivery (bus.SubscribeAll relying on BlockPublishUntilSubscriberAck for read-your-writes) plus projectionhost.Host for checkpointed, crash-restarting, DLQ-guarded catch-up is precisely the split the library's projection-tiers doc prescribes. The per-aggregate mutex-guarded version gate is a justified addition (stronger than the library's dedup.Ring event-ID ring, which cannot prevent stale-event resurrection). The only defect in this area is the DLQ volatility covered above.

Fully Leveraged

Storage lifecycle, codec choice, and version hygiene

store_factory.go · stack.go:106-132 · go.mod:44-63

SQLite is opened, schema-initialized, and WAL-enabled through the library's own helpers with pool constraints applied after; memory and SQLite backends are selected behind one config knob. CBOR (not JSON) payloads keep event storage compact. And every direct dependency sits at the latest published release — event v4.9.0, command v4.8.1, storage v4.8.1, watermill v4.5.1 — with the deprecated surface (stack presets, transports, VersionedStore) deliberately untouched.

04Considered and correctly not adopted

An honest utilization audit is not a maximalism contest. These library capabilities are deliberately out of scope for a single-aggregate, pull-only mirror (ADR-0004) — not adopting them is a decision, not a gap.

Capability Why not applicable
Encryption / signingMirror of public GitHub activity in local SQLite; no sensitive payloads or transit
Scheduling, Deriver (sagas)Single aggregate, no process management; sync cadence belongs to the consumer
Graph projections, metaengine, kv/listing tiersOne flat Item projection with SQL filtering; metaengine is experimental and the SQL view store is deprecated for v5
dedup.RingPer-aggregate version gate is strictly stronger than event-ID ring dedup
State cache / load coalescingStreams are 1-3 events; single-writer with per-source mutex — nothing to dedup
WaitForVersionSynchronous bus delivery already guarantees read-your-writes
Dispatch idempotency / command DLQSynchronous dispatch returns errors to callers; the decider no-ops unchanged items (natural idempotency)
