📊 Executive Summary

Go-LocalSync is computationally efficient — its in-memory fast paths are zero-allocation and its CRDT primitives benchmark in the low-nanosecond range. The critical weaknesses are all I/O-shaped: SQLite is configured without WAL mode and locked to a single connection, the sync loop is fully sequential, and network pagination has no concurrency. These are architectural decisions that are straightforward to fix without touching domain logic.

Bottom line: For a local-first single-user tool, performance is more than adequate. The system will handle ~20,000 items/sec in memory mode and ~2,000 items/sec with SQLite. The gaps become relevant only at scale (>50k items) or under concurrent load. All issues identified are configuration and loop-level fixes — no fundamental redesign needed.

SHA256 Aggregate ID — No Cache

Doc vs code mismatch: AGENTS.md claims a sync.Map cache exists for aggregate IDs, but pkg/cqrs/aggregate_id.go has no cache. The SHA256 hash + hex encoding + ParseAggregateID runs on every SyncItems call for every item, even items that haven't changed. For 1,000 unchanged items this is ~200µs of pure recomputation that a cache would eliminate.

Logging Overhead in Hot Path

The middleware.EventLogging middleware logs 2 structured lines per event at INFO level (dispatching + succeeded), plus the commandLoggingMiddleware adds a third. For a 1,000-item sync that's 3,000 log lines. Even with charm.land/log's efficient implementation, this adds measurable overhead — the benchmark output above shows ~40µs per item with logging vs ~5µs for unchanged items where the decider short-circuits before logging fires.

SQLite Configuration Gap

The go-cqrs-lite storage module provides SQLiteEnableWAL() and documents it in its README: 

storage.SQLiteEnableWAL(ctx, db)   // write-ahead logging for performance

But pkg/cqrs/store_factory.go only calls ConfigureTursoPool(db) — which internally just does db.SetMaxOpenConns(1). WAL mode is never enabled. The result:

  • Every write acquires an exclusive lock on the database file
  • Reads are blocked during writes (no concurrent read/write)
  • Only 1 connection exists — no parallel query execution at all
  • fsync on every commit (no group commit)

Write Amplification

Operation SQLite Writes Read Model Writes Total I/O
Sync 1 new item 1 event INSERT + 1 snapshot (every 10th) + 1 RM upsert INSERT OR REPLACE ~3 disk writes
Sync 100 new items 100 event INSERTs + 10 snapshots + 100 RM upserts 100 INSERT OR REPLACE ~210 disk writes
Sync 100 unchanged 0 events + 0 snapshots + 0 RM writes 0 0 disk writes idempotent
Delete 1 item 1 event INSERT + 1 RM DELETE DELETE ~2 disk writes
Each item sync is a separate transaction. The SyncItems loop dispatches commands one at a time through CommandDispatcher.Dispatch(). For 100 items, that's 100 separate BEGIN…COMMIT cycles on SQLite. A batch transaction would reduce this to 1 fsync for the entire batch — typically a 10–50× improvement on disk-backed SQLite.

HTTP Client Issues

  • Default transport MaxIdleConnsPerHost = 2. Go's http.DefaultTransport limits idle connections to 2 per host. For sequential requests this is fine, but if pages were fetched concurrently, this would bottleneck connection reuse.
  • No timeout configured. oauth2.NewClient() uses the default HTTP client with no explicit timeout. A hung GitHub API call blocks indefinitely (until context cancellation).
  • No ETag / conditional requests. GitHub supports If-None-Match headers for conditional requests (returns 304, costs 0 rate limit points). Not implemented.
  • Full JSON marshal on every event. convertEvent() calls json.Marshal(e) for every GitHub event, storing the full JSON as RawJSON. This adds ~1–2µs of CPU + ~1KB of memory per event, even if RawJSON is never read back.

🔀 Concurrency Analysis

Locking strategy, parallelism opportunities, and thread-safety characteristics.

Current Concurrency Model

Component Lock Strategy Parallel? Risk
MemoryReadModel sync.RWMutex — RLock for reads, Lock for writes concurrent reads List/Count hold RLock during full O(n) scan
SyncItems loop None — runs on caller's goroutine sequential 100 items = 100 sequential dispatches
CommandDispatcher None — synchronous dispatch sequential Each command blocks until projection completes
event.Bus (memory) Synchronous SubscribeAll inline Projection runs inside the publish call
SQLite backend SetMaxOpenConns(1) serialized All DB ops go through 1 connection
Projection Runner Background goroutine + checkpoint async replay Journal replay on restart runs in background

RWMutex Done Right good pattern

The MemoryReadModel correctly uses sync.RWMutex with RLock for all read operations (List, Count, GetTypes, Get) and Lock only for mutations (Upsert, Delete). This allows unlimited concurrent readers. The trade-off: List and Count hold the read lock for the entire O(n) scan, which blocks writers for the scan duration. For 10,000 items this is ~800µs per scan — negligible for a local tool.

Missing Parallelism Opportunities

  • SyncItems batch: Items are independent — each gets its own aggregate ID. A worker pool with N goroutines could sync items in parallel (memory backend only — SQLite's single connection would serialize anyway).
  • FetchAll pages: GitHub pagination could use errgroup.Group to fetch pages concurrently. Link headers provide next URLs. This would cut network time by ~N× (N = maxPages).
  • Projection: Could be decoupled from publish using a buffered channel + worker goroutine. Trades consistency for throughput.

Race Condition Safety verified

The readmodel_concurrent_test.go file includes 3 race-detector tests (-race flag): 10 writers × 50 items, 20 readers × 100 reads, and contested key upsert/delete. All pass cleanly. The memory backend is thread-safe.

🔍 Detailed Findings & Recommendations

Ranked by severity (P0 = critical, P3 = minor). Each finding includes root cause, impact, and fix.

SQLite WAL mode not enabled store_factory.go
P0 · Disk
createSQLiteStore() calls cqrsstorage.ConfigureTursoPool(db) (which just sets SetMaxOpenConns(1)) but never calls cqrsstorage.SQLiteEnableWAL(ctx, db). The go-cqrs-lite storage module provides this function and its README explicitly says to call it. Without WAL, SQLite uses DELETE journal mode — every write takes an exclusive lock, blocking all reads.
Add cqrsstorage.SQLiteEnableWAL(ctx, db) after OpenSQLite in store_factory.go:73. WAL allows concurrent readers during writes and reduces fsync overhead. Expected improvement: 3–10× faster SQLite writes, unblocked concurrent reads.
Impact: All SQLite operations. Effort: 1 line. Risk: None — WAL is strictly better for this use case.
No batch event writes — 1 transaction per item stack.go:SyncItems
P0 · Disk/CPU
The SyncItems loop dispatches each item through CommandDispatcher.Dispatch() individually. Each dispatch → repo.Execute() → event store append → bus publish → projection. For 1,000 items with SQLite, this means 1,000 separate BEGIN…COMMIT cycles and 1,000 fsyncs.
Wrap the SyncItems loop in a single transaction, or add a SyncItemsBatch method that groups events. Alternatively, increase SetMaxOpenConns to allow some parallelism (only safe with WAL). Expected improvement: 10–50× faster batch syncs on disk-backed SQLite.
Impact: Batch sync throughput. Effort: Medium (transaction boundary in decider repo). Risk: Partial failure semantics change.
N+1 query in GetStats sync.go:GetStats
P0 · CPU/Disk
GetStats() calls Count() for the total, then GetTypes(), then Count() again for each type. For 5 item types, that's 6 full-table scans. On 10,000 items this is 6 × O(n) scans = ~60,000 item comparisons.
Replace with a single SELECT type, COUNT(*) FROM sync_items GROUP BY type query. Add a CountByType() method to the ReadModel interface. Expected improvement: N× fewer queries (N = number of types).
Impact: Stats endpoint, CLI --stats. Effort: Low. Risk: None.
Sequential pagination — no concurrent page fetch client.go:FetchAll
P1 · Network
FetchAll loops for page := 1; page <= maxPages and calls Fetch() sequentially. Each page waits for the HTTP response of the previous page before starting. For 10 pages at ~200ms/round-trip, total time is ~2 seconds (sequential) vs ~200ms (concurrent).
Use errgroup.WithContext to fetch pages concurrently with a bounded goroutine pool. Parse Link headers to discover total pages. Expected improvement: ~N× faster network fetch (N = pages).
Impact: Sync wall-clock time. Effort: Medium. Risk: Rate limit exhaustion if not bounded.
Redundant rate-limit API call before every fetch client_retry.go:waitForRateLimit
P1 · Network
waitForRateLimit() calls c.client.RateLimit.Get(ctx) — a live API call to GitHub — before every single page fetch. For 10 pages, that's 10 extra API calls that each consume a rate-limit point. The rate limit info is also available in the response headers of every API call (X-RateLimit-Remaining).
Cache rate-limit info from the Response headers of the previous fetch call. Only call RateLimit.Get() on the first fetch or when the cache is stale. Expected improvement: 50% fewer API calls.
Impact: API quota consumption. Effort: Low. Risk: None.
Excessive SQLite row-scan allocations sqlite_scan.go
P1 · RAM/CPU
BenchmarkSQLiteReadModel_List shows 1,840 allocations for 100 rows (18.4 allocs/row). Each row scan creates a scannedItem struct, parses a ULID, creates 6 branded IDs via NewExternalID/NewProviderID/..., and constructs a model.Item. This generates significant GC pressure under load.
Use sql.RawBytes for string columns to avoid copy allocations. Pre-allocate the result slice with make([]*model.Item, 0, estimatedCount). Consider sync.Pool for the scannedItem scratch struct. Expected improvement: ~70% fewer allocations.
Impact: GC pressure on list queries. Effort: Medium. Risk: Low — scan logic stays the same.
Memory ReadModel is O(n) full scan — no secondary indexes memory_readmodel.go
P1 · CPU
List, Count, and GetTypes all iterate the entire items map on every call. For 10,000 items, List takes ~800µs and Count ~400µs. The memory backend has no index structures (by type, by actor, by source).
Add secondary maps (map[id.EventTypeID]map[string]*model.Item) maintained on Upsert/Delete. Or accept O(n) for the memory backend (it's designed for dev/testing) and focus optimization on SQLite. Verdict: Acceptable for the memory backend's intended use case. Document the scaling limit.
Impact: Memory backend at scale. Effort: Medium. Risk: Medium — index maintenance adds complexity.
SHA256 aggregate ID recomputed every call — no cache aggregate_id.go
P2 · CPU
AggregateID() computes sha256.Sum256 + hex.EncodeToString + ParseAggregateID on every call. For 1,000 unchanged items, this is ~200µs of pure recomputation. AGENTS.md claims a sync.Map cache exists but the code has none.
Add a sync.Map cache keyed by source + ":" + externalID. Aggregate IDs are deterministic and immutable — the cache never invalidates. Expected improvement: ~200µs saved per 1,000-item sync with unchanged items.
Impact: Minor CPU savings. Effort: 10 lines. Risk: None.
Logging middleware fires on every event at INFO level middleware.go
P2 · CPU/RAM
EventLogging logs 2 lines per event (dispatching + succeeded/failed) plus commandLoggingMiddleware logs 1 more. For 1,000 items: 3,000 log lines. Even with charm.land/log's efficiency, structured logging involves string formatting, field allocation, and I/O. The benchmark output demonstrates this clearly — logging dominates the per-item timing.
Default to log.DebugLevel for event/command middleware. Add a --verbose flag to opt into INFO. Or sample logging (1 per N events). Expected improvement: ~40% faster SyncItems with logging suppressed.
Impact: Batch sync throughput. Effort: Low. Risk: Reduced observability — mitigated by opt-in flag.
No HTTP client timeout configured client.go:NewClient
P2 · Network
oauth2.NewClient() wraps Go's default HTTP client which has no timeout. A stalled GitHub API connection will block the sync goroutine indefinitely (until context cancellation).
Create a custom *http.Client with Timeout: 30 * time.Second and pass it to oauth2.NewClient or gh.NewClient.
Impact: Hang resilience. Effort: 3 lines. Risk: None.
No ETag / conditional request support client.go
P2 · Network
GitHub API responses include ETag headers. Re-sending If-None-Match returns 304 Not Modified and costs 0 rate-limit points. For incremental syncs where most items haven't changed, this would dramatically reduce API quota consumption.
Cache ETag per URL. On re-fetch, send If-None-Match header. Handle 304 responses gracefully (skip item processing).
Impact: API quota for incremental syncs. Effort: Medium. Risk: Low.
Event store grows unbounded — no compaction decider.Repository
P3 · Disk
Every state change creates events that are stored forever. Snapshots (EveryNEvents(10)) cap replay cost but don't remove old events. Over months of syncing, the event store can grow significantly (each event ~800B with RawJSON).
Add an event compaction/tombstone strategy: after snapshotting, mark old events as archived or move to cold storage. This is a future concern — not urgent for a local-first tool.
Impact: Long-term disk usage. Effort: High. Risk: Medium — compaction must preserve audit trail semantics.
Full JSON marshal on every GitHub event client.go:convertEvent
P3 · CPU/RAM
convertEvent() calls json.Marshal(e) on every GitHub event to store RawJSON. This adds ~1–2µs CPU + ~1KB allocation per event. If RawJSON is rarely read back (e.g., only for debugging), this is wasted work.
Make RawJSON storage opt-in via a config flag. Or lazy-marshal on first access. For now, acceptable — the overhead is small and RawJSON provides audit value.
Impact: Minor per-event overhead. Effort: Low. Risk: None.
Pure-Go SQLite driver (modernc.org/sqlite) go.mod
P3 · Disk/CPU
modernc.org/sqlite is a transpiled C-to-Go SQLite. It avoids CGo (simpler builds, cross-compilation) but is 1.5–2× slower than mattn/go-sqlite3 for I/O-heavy workloads. The tradeoff is intentional and correct for a local-first tool — CGo adds cross-compilation complexity and build-time dependencies.
No action needed. The pure-Go tradeoff is the right call for this project. If SQLite performance becomes critical, consider CGo as an opt-in build tag. WAL mode + batching (see P0-1, P0-2) would provide more benefit than switching drivers.
Impact: SQLite throughput ceiling. Effort: N/A. Risk: N/A.

✅ What's Done Right

Performance strengths worth preserving.

Zero-allocation adapter layer
strength
toDataItem and fromDataItem benchmark at 0.25 ns with 0 allocations. The boundary between provider DTOs and domain entities is a pure struct copy — no boxing, no reflection, no interface dispatch. This is textbook Go performance.
CRDT primitives are allocation-free
strength
VectorClock operations (Increment, Merge, Cmp) all benchmark at 0 B/op, 0 allocs/op. The LWWResolver constructor is 0.6 ns. Conflict resolution adds negligible overhead to the sync path.
Idempotent sync — unchanged items are nearly free
strength
hasChanged() short-circuits before any event creation. Unchanged items skip event store writes, bus publication, projection, and read model updates. The per-item cost drops from ~45µs to ~5µs (just the aggregate load + comparison). For re-syncs where 90% of items are unchanged, this is 9× faster than naive upsert-all.
Correct RWMutex usage with race-detector tests
strength
The MemoryReadModel uses RLock for all reads and Lock for writes. Three dedicated concurrent-access tests run under -race with 10 writers and 20 readers. No data races detected.
Well-designed SQLite index strategy
strength
5 indexes cover all filter combinations: type, created_at (default sort), actor, repo_name, and a composite (type, created_at DESC) for the common "filter by type + sort by date" query. The composite primary key (source, source_id) doubles as an index for source-based lookups.
Branded IDs compile away to zero cost
strength
The phantom-type branded IDs from go-branded-id provide compile-time type safety with zero runtime overhead. id.ID[Brand, string] is a struct wrapping a single value — the compiler optimizes it to the underlying type. .Get() is an inlined field access.
